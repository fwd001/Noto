## 3. 数据安全与同步正确性：这一版真的证明了什么

按优先级阶梯的头两档（数据安全 > 同步正确性）逐条给证据。**每条都对应上面台账里的一个命令**，不是设计意图。

- **崩溃不丢数据**：10 个提交点逐个"真死进程"再重启，两台设备逐条一致、outbox 归零；清单**先写分段、后提交索引**，所以不会出现"索引引用一个还不存在的对象"（INV-09）。
- **换设备自动恢复**：260 条与 1000 条两档实测，空库设备入伙后**一条不少、内容一字不差**（(标题, 内容哈希) 逐条相等），FTS 行数 == 笔记数。
- **不谎报同步状态**：被每轮请求预算截断的那一轮，徽标只能是"正在同步"；追平后才回"已同步"。调度器的续跑判据是"这一轮真的推进了"，没进展就退回常规节拍（不再无界热转圈）。
- **删除语义**：删除 → 回收站 → 恢复 → 永久删除这条链有端到端证据；`purged` 墓碑会传播，不会出现"永久删除后被另一台重新上传而复活"。
- **冲突不静默覆盖**：分叉时保留双方并落冲突收件箱；`rev`/`content_hash` 的 CAS 与 304 快路径都有用例。
- **附件**：内容寻址 + 下载按窗口续传（`.part`），拼完先自核 sha256 才落正式 blob；服务器不支持 Range 时老实整块取。
- **本轮新查清并修好的一条真丢数据路径**（原台账里没有，是黑盒 lane 抖出来的）：autosave 的**在飞回包**代表过去那一版，回来却清了 `dirty`；随后任何一次同一笔记的回读就有理由把正文换回旧版 —— 表现是"屏幕上有字、库里是空正文、右下角写着已保存"。现在回包对不上当前正文就保持 dirty、不应用回包、另起一轮；配一条整链回归测试并做过变异。
- **默认本跨设备收敛**：以前每台设备各造一个 id，两台入伙后互相拉回对方的那一份，侧栏长出两个「默认本」。现在是固定 id，清单里就一个条目。
- **门禁本身可信**：本轮每条新/改的门禁都先证明它会 FAIL（变异测试）才采信。这一轮里它抓到过：我自己插桩写错（少 import）导致"零条日志"被误读、一次假绿灯（逐条比对被 500 行默认上限截断）、以及上面那条竞态。

## 6. 交给用户怎么测（§47 最小闭环 + §49 所需权限）

**要打开的权限/环境**：
- Windows Defender 防火墙首次会问"是否允许 notera-desktop 访问网络" → **允许专用网络**（用于访问你的 WebDAV）。不开的话同步会一直显示离线，本地使用不受影响（这是设计如此：网络失败绝不阻塞本地编辑）。
- 一个**可写的 WebDAV 端点**（自建 Nextcloud/Apache mod_dav 皆可），账号密码交给应用即可；不需要管理员权限。
- 想验"换设备自动恢复"：再起一份程序并指到**另一个数据目录**，配同一个 WebDAV 账号即可当第二台设备。

**建议按这个顺序点**（每步都只依赖界面）：
1. 新建笔记 → 立刻打字 → 列表标题应是你打的那句（这条就是本轮修掉的竞态，重点回归）。
2. 改一条、删一条 → 回收站看得见 → 恢复 → 永久删除。
3. 插一张图片 → 屏幕上真的解出像素 → 刷新/重开还在。
4. 设置里配 WebDAV → 能力块读回探测结果 → 徽标走到"已同步"。
5. 第二台设备开机 → 观察徽标是"正在同步"（不许提前说已同步）→ 追平后逐条比对。
6. 中途拔网线/关 Wi-Fi 再恢复 → 继续写 → 恢复后应自动追平，两机逐条一致。
7. **托盘**（本轮新增）：任务栏右下角应出现 Notera 图标。左键点它 → 窗口隐藏/唤回都该由这一次点击决定；右键 → 菜单四项（显示/隐藏、新建笔记、立即同步、退出），"退出"应真的退干净（任务管理器里不再有 `notera-desktop.exe`）。
   - 设置页里那条**「关闭时留在系统托盘」默认是关的**：关着时点窗口右上角 × = 正常退出；勾上之后再点 × 才是收进托盘。两种情况都要各点一次。
   - 如果这台机器上托盘没挂上（企业策略、图标被系统拒绝），设置页那两项应自动变成"这台设备不支持常驻托盘"，并且右下角应弹一条 Toast 说明降级 —— **不该**出现"图标没有但界面说有"的样子。
8. **`.enex` 导入**（本轮新增）：从 Evernote「导出笔记」拿一个 `.enex`（**建议先只导一条**），把它的完整路径填到设置页 →数据 → "输入路径"那个框里，然后点**「导入这个文件（.enex / Markdown）」**。
   - 该看到的：一个 `.enex` 里的**多条**笔记一次全进来（不是一条）；标题列显示的是 Evernote 的标题而不是正文第一行；正文里内嵌的图片在笔记里直接解出像素（不是占位框）；"只挂在笔记上、没内嵌"的附件（如 PDF）出现在文末。
   - 该看到的第二件事：**按钮下面那份清单**。Evernote 的标签（`<tag>`）、创建/修改时间、表格结构，本库当前表达不了 —— 它们必须被逐条写出来，而不是悄悄消失。如果你看到一条笔记的标签不见了却没任何说明，那是缺陷。
   - 重复点一次同一个文件：应该**一条都不新建**（提示"重复 N"），库里不产生副本。
   - 已知的界：`.enex` 走的是和其它导入文件同一道体积闸门（**8 MiB**）。真实带图导出很容易超，超了会看到一条明确的失败而不是导入到一半。这是本轮记下的限制（TEST-PLAN IMP-06），不是 bug 现场。
   - 需要确认的产品取向（不属 defect）：标签要不要成为本库的一等概念、导入时是否保留 Evernote 的时间戳 —— 两者都要动 schema/合并语义，按 §51 等你拍板。
9. **全局快捷键**（本轮新增）：把焦点切到**别的应用**（记事本/浏览器），按 `Ctrl+Alt+N` → Notera 应新建一条笔记并把窗口带到前台；按 `Ctrl+Alt+I` → 窗口显示/隐藏。
   - 这两条组合键**可能在你的机器上被别的应用占着**（输入法、截图、显卡驱动热键最常见）。占用的表现是：Notera 完全不响应，而那个别的应用在响应。
   - **按现在的实现，注册是"全成才算成"**：只要有一条被占，`globalShortcuts` 就报 false，设置页里那两行快捷键**一起消失**并弹一条降级 Toast（不会留下"显示着但按了没反应"的假象）。所以"看不到那两行"= 这台机器上至少一条没注册上，属于**已告知的降级**，不是界面漏了。要按键分别声明能力（一条成就算半成）需要先定产品取向，本轮没做。
   - 需要确认的产品取向（不属 defect）：`Ctrl+Alt+I` 与部分 IDE/工具冲突时是否改成可配置 —— 现在**不可配置**，要改键请先说。

10. **对面的删除撞你的修改**（本轮把这条链修通并钉了 CF-13…17 五条门禁，值得手测一遍）：两台设备配同一个 WebDAV → A 建一条并等同步 → B 拉到 → **A 把它删除**并同步 → 在 B 上改这条笔记（先别同步）→ 再让 B 同步。
   - 该看到的：B 的列表里这条笔记**仍在**，且它那一行带着 ⚠「这条在别的设备上有了分歧，等你处理」；侧栏「需要处理的版本」出现条数。
   - 点开卡片：右栏应当显示 **A 删除前的那段正文** —— 不是哈希，也不是你在 B 上改的这一版。若显示"没能从服务器取回那一版"，说明那一轮没取到（预算或网络），再点一次同步即可；两种情况都**不该**让你看到两份一样的文字并排。
   - 三个按钮的真实语义（已按实测钉死，不是我推测的）：**用服务器这一版替换** → 这条在 B 也进回收站，而 B 那一版仍以副本形式留着；**保留两份** → B 内容不动，且 A 那台的删除**不会**因此复活（两边各得其所，这一条是今天实测纠正了我自己预期之后钉住的）；**用我这一版** → 正文与副本互换，两条都重新公告。
   - 每个按钮各按一次，然后回到 A 那台同步，看它"以为的状态"有没有被 B 悄悄改掉 —— 按现在的实现不应该出现静默覆盖。

11. **零引用的附件会被回收，但是"先挪走、30 天后才真删"**（本批新增，值得手测一遍，因为这是第一次有代码主动让字节离开你的磁盘）：
   - 做法：建一条笔记插一张图 → 等徽标到"已同步"（**图必须在服务器上有副本，回收才认它**）→ 把这条笔记删进回收站，再**永久删除**。
   - 该看到的：几轮之内（附件轮 20 s 一跳，一轮最多收 200 条）`<数据目录>\attachments\<两位hex>\` 里那个文件**不见了**，而旁边多出一个 `<数据目录>\attachments-quarantine\<两位hex>\<同一个 sha>`，**字节数一模一样** —— 是"挪走"，不是"删掉"。
   - 撤销那一半（这条最有意思）：在这 30 天里，你在任何一条笔记里再插入**同一个文件**（内容寻址 = 同一个 sha），那张图应该**当场就能显示**，而且**一次网络都不走** —— 把网线拔了再试也一样补得回来。
   - 30 天之后那份才会被真删。这一步不必真等 30 天：想立刻看效果可以让我按"未来的宽限期界"跑一次回收，把结果给你看。
   - 要提前说清的两条边界：**没配 WebDAV 账号的那台设备不会跑回收**（触发点在同步的附件轮里），那条 `attachments/` 目前还是会一直涨；以及**服务器上的对象本批不回收**（只清本机盘）。另外在笔记里"删掉一张图"目前**不释放引用**（链接表只有笔记被删才减少），所以回收的收益现在集中在"永久删除笔记"这一类 —— 判据是故意偏保守的：宁可少收，绝不错收。

12. **口令现在落在你自己机器的凭据管理器里**（0.0.29 起 —— 这是这批改动里最该你亲自看一眼的一条）：第 4 步配完账号，打开命令行敲 `cmdkey /list`，应该能看到一条 `notera:webdav:<那串 id>`（配了应用代理会多一条 `notera:proxy:<id>`）。

- **G24 本机把一条笔记从回收站里恢复出来，而对面已经把它永久删除 —— 恢复被静默公告出去，等于用同步把永久删除的数据复活了（2026-09-29 实测；状态 = **已修，0.0.40**）**：

  `轮次(冲突/拒收/结局) = [(0, 0, Converged), (0,0,NoOp)×3]`、B 上 `rev=3 / sync_rev=3 / 删=false`、
  **卡片 0 张**、而服务器盘上那条记录变成 **`purged=false / payload 非空 / 含正文=true`（563 B）** ——
  服务器与任何后接入的设备都会重新拿到那条"已被永久删除"的笔记，而两台的界面都说"已同步"。
  这条撞的是主指令的一条明令禁止（**不许靠同步复活已删除的数据**），所以档位是 P1（数据安全 + 同步正确性）。
  **根因（一句话）**：永久删除的公告信封**仍然带着最后一版的 `hash`**（清单条目 `h` 就是它），
  而 P11 那一格的判据写的是"远端已删 **且不是永久删除**"（`&& !r.purged`）—— 于是"对面永久删除 + 本机恢复"
  这一对没进 P11，掉到 P7 的"内容相同即收敛"上：两侧正文哈希当然相同（本来就是同一版），
  本机 rev 更高 ⇒ `Push` ⇒ 把正文 PUT 回服务器。
  **修两处**：① 计划层 P11 改成 `local_changed && (r.deleted_at.is_some() || r.purged)` —— **永久删除也是一种"远端已删"**，
  这一格从此走冲突路径（§8.4 承诺的那句）；② 卡片那一侧的「用服务器那一版」以前只问"对面是不是删除态"，
  对墓碑只落**软删**（行还留在回收站可恢复，而用户以为接受的是永久删除）——

- **G23 一条带附件的笔记被永久删除之后，服务器上的那些附件字节还在（2026-09-29 实测；状态 = **BLOCKED，等产品拍板口径**）**：
  量具是 `notera-host/tests/sync_once.rs::probe_purge_and_remote_attachment_blobs`（`#[ignore]`，只出数不判绿；
  跑法 `cargo test -p notera-host --test sync_once -- --ignored --nocapture`）。形状：A 建一条笔记 + 用产品路径挂一个 blob
  （`attach_blob` 之后把 `sha256` 引用写进正文，再走 `run_attachment_round`）→ B 追平（B 那台读到的附件状态是
  `("available","present")`）→ A `purge_note` 并公告 → 两边各再跑几轮。量到的四件事实：
  ① 服务器那条笔记记录被换成 **369 B 的墓碑公告**（`purged=true / payload=null`，正文没了 —— 这一半 SY-DEL-02 已钉住）；
  ② A 留下 `tombstones_purged=1`；③ **B 那台对这个 sha 的引用数归 0**；
  ④ **而 `.notes/attachments/d4/d4cf4296…:11B` 原样躺在服务器上**（生产里那就是一张图或一份 PDF 的字节）。
  影响：**"永久删除"这句话目前只覆盖笔记正文，不覆盖附件**。用户在回收站里"彻底删除"一条带截图的笔记之后，
  他自己的服务器上那份截图仍然可被任何拿到凭据的人取回 —— 而本机那一侧我们做了 GC（隔离区 + 可撤销期 + 销毁前向服务器复查），
  **两侧口径不一致**，这个不对称本身就是让人误以为"删干净了"的来源。
  为什么没直接修：远端销毁是**带破坏性的一支**，而"这个 blob 还有没有别人在用"在本机是按 `note_attachments` 派生的引用计数算的，
  **跨设备/跨账户的引用只有服务器知道**。一台设备看见自己引用归零就发 `DELETE`，可能把另一台设备上还活着的笔记的图删掉；
  要做对，得先定"谁有权删"（发起删除那台？每台都复查自己的引用后再删？还是只在服务器支持时由一个 GC 轮做？）。
  解除条件：① **用户拍板口径**（§51）——"永久删除"要不要连附件一起从服务器上消失；
  ② 若要，需一次架构评审决定删的权限与时机（§9：这是一条新的远端写/删路径，不是改几行）；
  ③ 判据形状已经想好：把上面那条量具升成断言"永久删除传播之后服务器上不许有带这个 sha 的对象"，
  并要求它**今天就是红的**（红了才说明真的在盯这件事），配套变异 = 把 DELETE 跳过 → 判据必须还红。
  ④ 顺带一并拍的：`attachments` 那一条在清单里是独立类型（`t="a"`），所以"笔记 purged 而附件对象还在"这件事
  在协议层是**可看见的**，不是只能靠客户端自觉。

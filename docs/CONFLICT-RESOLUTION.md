# CONFLICT-RESOLUTION

Notera 的冲突检测、合并与删除语义。规范性文档。

关联：[SYNC-PROTOCOL.md](./SYNC-PROTOCOL.md) §7 判定表 · [DATA-MODEL.md](./DATA-MODEL.md) §4 revision / §10 富文本 · ADR-0005 / 0006 / 0007 / 0008

---

## 0. 唯一不可协商的目标

> **用户输入过的内容，不会因为同步、冲突、崩溃或另一台设备的操作而静默消失。**

冲突解决"不够聪明"是可以接受的（多留一份副本、多点一次按钮）；冲突解决"聪明到替用户做决定并丢掉一份内容"是不可接受的。本文所有规则都由此推导。

## 1. 什么才算冲突

### 1.1 判定式

```text
冲突 ⟺  L.rev ≠ L.sync_rev        （本地自上次一致点以来改过）
        ∧  R.rev ≠ L.sync_rev      （远端也改过）
        ∧  H(local) ≠ H(remote)    （最终内容确实不同）
```

`L.sync_rev` 是**双端确认过的共同祖先**（定义见 DATA-MODEL §4.3）。因此三方齐备：

| 输入 | 来源 |
|---|---|
| base | `note_revisions(note_id, rev = sync_rev).doc` |
| local | `notes.doc`（`rev = L.rev`） |
| remote | `records/note/<id>.json` 的 `payload` |

### 1.2 不算冲突的情形（必须显式排除，否则会产生大量假冲突）

| 情形 | 判定 | 依据 |
|---|---|---|
| 两侧最终内容相同（各自打开又保存、回环同步） | 收敛，`rev := R.rev` —— **按实补一句（2026-09-29）**：这句原来给的是 `NoOp`，而"收敛"必须**有动作可走**才成立。现在两侧都改而正文哈希相同时：rev 高的一边把记录公告出去（Push），低的一边把对面那一版拉下来（Pull），真相等才是无事可做；对面那一版一落地，本机该实体**还没走完的上写待办**同时标 `superseded`（I2 保证 `env.rev ≥` 本地 head，而那些待办再也推不出去 —— 不结就是"待处理任务永远不掉"，两台设备实测过）。这里**不能**改成"直接标成已同步"：`content_hash` 不含 `pinned`/`color`/`folder_id`，那样会静默丢掉标量变更。判据 SY-CONV-01 | SYNC-PROTOCOL P7 |
| 只有本地改 | Push | P5 |
| 只有远端改 | Pull | P6 |
| 仅 `pinned` / `color` 等标量属性不同 | 属性级合并（§4），不进冲突收件箱 | — |
| 仅 `folder_id` 不同且笔记正文一致 | 移动合并（§4.3） | — |
| 两侧改同一文档的**不同块** | 块级自动合并（§3） | — |
| 一侧改、另一侧删除 | **是**冲突（§5） | P11 |

### 1.3 禁止的判定方式

* 禁止用 `updated_at` / mtime / 服务器时间比较新旧（时钟不可信，R3）。
* 禁止"整篇文档二选一"作为默认策略。
* 禁止用"远端文件不存在"推断"用户删了它"（SYNC-PROTOCOL §10）。

## 2. 合并流水线

```text
检测冲突
  ↓
① 信封级：kind/id 一致？协议版本支持？            否 → 只读 + 上报
  ↓
② 文档级：H(local) == H(remote)？                  是 → 收敛，结束
  ↓
③ 块级三方合并（§3）                               成功 → AutoMerged，记 auto_merged=1
  ↓
④ 标量属性合并（§4）
  ↓
⑤ 仍有无法判定的块                                 → 生成冲突记录 + 冲突副本（§6）
```

第 ③ 步成功时**不产生任何用户可见的冲突提示**，只在 `sync_conflicts` 留一条 `auto_merged=1` 的记录供审计。这是"用户不该感知同步系统"（§2 产品目标）的落点。

> **按实（2026-09-29，一次"把带编号的承诺逐条对代码"的清扫查出来的）**：这条流水线**只有 ①②⑤ 在产品里跑**。
> ③ 那条块级三方合并（`notera-richtext::merge`，§3）**没有任何生产调用点** —— 全仓 `grep` 只命中它自己的
> 定义、crate 的 re-export 与单元/属性测试（`crates/notera-richtext/src/merge.rs`、`merge_tests.rs`、
> `tests/api_contract.rs`），同步侧一条路径都不经过它；`auto_merged` 这一列在库里**从来没有为真过**
> （所有生产写入点都传 `false`）。④ 标量属性合并也不存在（`pinned` / `color` / `folder_id` 是"远端整行覆盖"）。
> 于是两侧都改正文时的**实际**策略就是 ⑤：本机那一版整份另存一条副本、正文整篇采纳对面那一版
> —— 内容不丢（副本读得回来，判据 `sync_once.rs::a_real_divergence_records_one_conflict_and_keeps_both_texts`），
> 但不是"逐块自动合并、用户不感知"。这一格记为缺口 **G15**（原因：接入它要同时改同步的决策与 rev/hash 口径，
> 属于总指令 §9 要求"先架构评审"的那类变更，本批没有擅自做）。§3 整节因此读作**设计与库能力**，
> 不是已交付的同步行为。

## 3. 块级三方合并

### 3.1 为什么按块而不是按字符

富文本模型（DATA-MODEL §10）保证**每个顶层块有稳定 `id`**，跨编辑不漂移。于是：

* 两人在同一段落各写一句 → 同 id 块两侧都改 → 块级冲突；
* 两人各写不同段落 / 一个改正文一个加图片 → 不同 id → 无损自动合并。

按字符做 diff（Myers 之类）在这里是**更弱**的方案：段落顺序漂移会让"同一段"对不齐，从而把可合并的场景误判为冲突。块 id 是应用自己维护的锚点，比文本相似度可靠。

### 3.2 算法（纯函数，`notera-richtext::merge`）

```text
输入 base, local, remote（均 normalize 过）
1. 建 id → block 映射；记录三方的顶层块顺序
2. 对每个 base 块 b：
   a. b 不在 local 且不在 remote          → 删除（无争议）
   b. b 不在 local 但 H 未变于 remote     → 采纳删除
   c. b 不在 remote 但 local 保留         → 保留 local（视为 local 未删）
   d. 两侧都在：
      - H(local_b)==H(base_b) → 取 remote_b
      - H(remote_b)==H(base_b) → 取 local_b
      - 两侧都改且 H 相等       → 取任一
      - 两侧都改且 H 不等       → 冲突块，进 §3.3 处理
3. 新增块（不在 base）：local-only / remote-only 都并入；
   两侧各加了一个内容相同的新块（同文本不同 id）→ 去重保留一个
4. 顺序：以 base 顺序为骨架插入；两侧都调整了顺序 → 顺序判为冲突
5. 输出 MergeOutcome
```

### 3.3 冲突块的降级顺序（依次尝试，任一成功即止）

| 级 | 条件 | 结果 |
|---|---|---|
| M1 | 一侧只是格式变化（`plain_text` 相同，marks/attrs 不同） | 采纳带格式的一侧，另一侧格式丢弃但记入审计 |
| M2 | 一侧是另一代的严格超集（`base ⊂ local ⊂ remote` 逐字符包含） | 采纳超集侧 |
| M3 | 两侧都是对 base 的纯追加（前缀相同） | 拼接两侧追加内容 |
| M4 | checklist 项：一侧勾选、一侧改文本 | 文本取改动侧，勾选状态取改动侧，冲突则默认未勾选并保留另一状态到 `unknown_attrs` |
| M5 | 以上都不成立 | **该块判冲突**，整篇走 §6 |

M1–M4 都是"能证明无损"才做，不是"看起来差不多"。合并结果必须满足：`H(merged) ≠ H(base)` 且 merged 包含两侧所有可辨识内容。

### 3.4 失败保护

自动合并产出的文档必须重新 `validate()` + `normalize()`；不通过则**丢弃合并结果**，退回 §6 保留双方。绝不写回一个未通过校验的文档。

## 4. 标量属性与结构字段合并

| 字段 | 规则 |
|---|---|
| `pinned` | OR（一侧固定即固定）；两侧都从 true 变 false 才为 false |
| `color` | 一侧为 null 取另一侧；都非 null 且不同 → 取 remote，local 值记入审计（不升级为冲突） |
| `name`（文件夹） | 两侧都改且不同 → 取 remote，local 值记审计并提示；文件夹不做冲突副本（副本文件夹会污染侧栏） |
| `folder_id`（笔记移动） | 一侧移动一侧未动 → 采纳移动；两侧移到不同文件夹 → 采纳 remote，记审计 |
| 文件夹 `parent_id` | 两侧都改 → 采纳 remote；**但落地会成环的那一支不写父**：其余字段与 rev 一起采纳（这一行照样 settle，不每轮重推），父保留本机现在的那个。于是两侧会在"这两个夹子摆在哪"上各自保留自己那一版 —— 有意为之：**位置分叉看得见、用户再移一次就能修，而环看不见也修不了**（这两个夹子从根走不到 → 侧栏里没有、里面的笔记也看不见；且下一次移动任何文件夹的递归查询永不返回）。判据 CY-01（两台真设备）/ CY-02（已有环的库不许卡死）。**目前不提示用户**这一格发生了 —— 那是一条记在 PRODUCTION-READINESS §7 的缺口，不是已实现的行为。旧文档这里写的"整体回退到 base 父级并记诊断"给不出来：文件夹没有存"共同祖先那一版的父"，实现不许承诺自己做不到的事 |
| `deleted_at` | 见 §5 |
| `attachments` 引用 | 并集（引用是内容的一部分，不因删除引用而丢 blob） |

原则：**属性冲突降级为"审计 + 提示"，内容冲突才升级为"收件箱 + 副本"**。用户不会为颜色产生挫败感，但会为丢字产生。

## 5. 删除语义（三处易错点）

### 5.1 删除 vs 修改（P11）

```text
设备 A：编辑笔记（rev 7→8）
设备 B：删除同一笔记（rev 7→8, deleted_at=T）
```

协议上两侧 `rev` 都大于 `sync_rev=7` → 真冲突。处置：

1. **保留内容**（数据安全 > 一切）：合并后笔记存活，`deleted_at=NULL`；
2. 写 `sync_conflicts(kind=delete_vs_edit)`；
3. UI 冲突收件箱给出两个明确动作：**"仍要删除"**（→ 永久删除流程，`rev` 再 +1 传播）或**"保留这份修改"**；

   > **落地时补的一条（2026-09-27）**：第 3 步右栏那颗"用这一版替换"当初只是把卡片改成 resolved —— 笔记还在正常列表里，而本机那个从未上行过的 head 下一轮带更高 rev 推上去，会把对面**已经确认**的删除覆盖回来。也就是"用户按了按钮、什么都没发生、还替别人撤销了删除"。现在 `App::resolve_conflict` 在 resolution 为 remote 时读冲突行挂着的服务器原始信封（`remote_wire`，迁移 0008）：里面写了 `deleted_at` 就照它删（本机内容早先已被 §5.1 第 1 步的副本留住），没带载荷就不动内容、只关卡片 —— 由面板那句"没能从服务器取回那一版"负责说明，不替用户猜。判据见 `conflict_payload_e2e.rs::accepting_the_remote_delete_actually_deletes_and_propagates_it`（两台真设备：接受之后 B 必须没有这条正常笔记，且两边再各追若干轮 A 那台仍是已删除，不许复活）。
   > **口径对齐（同日实现时定）**：第 3 步那句"仍要删除 → 永久删除流程"落地的是
   > **软删除 + `rev` 再 +1 传播**（笔记进回收站），不是当场 `purge` —— 误按一次就要付出
   > 不可逆的代价，方向不对。要真确认"永久"，用户在回收站里再按一次"彻底删除"，
   > 那条边已有门禁（TEST-PLAN 的回收站/彻底删除步，`verify-app` 第 24 步那一条）。

4. 在用户选择前，笔记显示在正常列表并带"⚠ 其他设备删除了这条"标记。

   **落地口径（2026-09-27，实现时对齐）**：标记画在**任何**有未裁决冲突的笔记行上，措辞是
   `list.contendedNote` = "这条在别的设备上有了分歧，等你处理"。为什么不写死"其他设备删除了这条"：
   冲突卡片不带类别（`ConflictDto` 里没有 kind），只有"删除 vs 修改"才这样说的话，
   别的分歧类型就会被画成空白 —— 而这一条存在的理由是**用户不必先想到去开面板**才知道
   这条笔记有分歧。验证：`scripts/verify-p11-panel.mjs` 第 9 步（真浏览器：列表里这条笔记
   仍在、正文仍是本机那一版、⚠ 恰好落在冲突那两条上而不是每行都有）。两个方向的变异都验过：
   把渲染条件改成无条件 `true` → 红在"3 行里 3 行都带标记"；把标记摘掉 → 红在"没有任何标记"。

不做"谁的时间晚听谁的"——那等于允许一台误删的设备吃掉另一台的编辑成果。

#### 5.1.1 被删那一版必须**看得见**（2026-09-27 用户拍板：按现在最佳体验，不做历史兼容）

上面第 3 步要求用户在两个动作之间选，但当前实现只给了他一个**哈希**：
`sync_conflicts` 只有 `remote_hash`，服务器那一版的正文从没到过本机（引擎只在打算
采纳时才拉记录，而 P11 刻意不自动采纳 —— 见 `notera-sync/src/lib.rs` 里
"只有 UpdateUpdate 走这条路"那段）。**看不见的选择不是选择**，所以这条按已决定处理，
不再是 §51 的待拍板项。实现切片（每步都要带门禁，别一次全做完再验）：

1. **引擎**：判定为 P11 / P11b 且远端是"软删未 purge"时，把那条记录的正文物料取回来
   一次，随冲突一起交给 `record_conflict`。约束：只在真的产生冲突时取（每轮罕见），
   并且**取失败绝不让冲突消失** —— 退回现在的哈希显示，同时把"这一版内容没取回来"
   作为一条具名说明给用户（§39 不许静默降级，也不许为了好看假装取到了）。
2. **存储**：迁移 0008 给 `sync_conflicts` 加 `remote_doc`（正文 JSON 原文）与
   `remote_updated_at`。第一版未发布，按决定不写兼容层；老行 `remote_doc IS NULL`
   就是"取回来失败/旧数据"的诚实表达，不要回填猜测值。
3. **命令面**：`conflicts` 的 DTO 加 `remotePreview`，复用 #26 已经实现的
   `preview_text`（别在 Rust 之外再写一份摘要逻辑）。
4. **界面**：冲突卡右栏从"一串哈希"换成那份正文 + 它的时间；两个动作的语义不变。
5. **门禁**（缺一不可，且要先变异再信）：
   - 两台真设备：B 删、A 在删后又改 → A 的冲突卡里必须出现 **B 那一版的正文文字**
     （断言打在屏幕上读回来的文本，不打卡片结构）；
   - 断言"取料失败时冲突仍然在册且带说明"（用 `notera-test-webdav` 的记录注入 500）；
   - 变异自证：把第 1 步的取料调用摘掉 → 第一条必须红；把失败分支改成 `?` 直接冒泡
     → 第二条必须红。

代价说清楚：一次冲突多一次 GET。这是**正确性换带宽**，方向与优先级阶梯一致
（同步正确性 > 性能），且只在真冲突上发生，不进空轮预算（`sync_cost` 那条门禁
盯的是空轮，不会因此变红——若变红了，说明取料被放错了位置）。

> **实现时踩到的一条，写给下一个读这里的人**：第一版把"读对面那一版"接在了
> `preview_text(id, rev)` 的回落上 —— 听起来顺理成章，实际是错的，而且错得很安静：
> `rev` 是**各设备自己的编号**，本机历史上同一个号常常是另一份内容，于是右栏读回来的是
> **本机这一版**。两台真设备的测试（`notera-host/tests/conflict_payload_e2e.rs`）第一次跑
> 就把它抓红了（断言是"右栏必须含被删那版的文字、且不得含本机那版的文字"）。
> 结论：**对面那一版只能由卡片自己带着**（`ConflictDto.remote_preview`，取自冲突行的
> `remote_wire`），永远不要按 `(noteId, remoteRev)` 去查本机历史 —— §6.1 那句
> "两边都用 noteId + 各自 rev 是不行的"对 P11 同样成立，尽管 P11 根本没有采纳这一步。

### 5.1.2 面板右栏那一份从哪儿来（2026-09-27 收口）

**规则只有一条**：冲突卡片的"对面那一版"永远由卡片自己携带（`ConflictDto.remote_preview`，
字节来自迁移 0008 的 `sync_conflicts.remote_wire`）；卡片没带，面板就说"没能从服务器取回
那一版"。界面**不许**按 `(noteId, remoteRev)` 回查本机修订历史 —— `rev` 是各设备自己的编号，
本机历史上同一个号往往是另一份内容，查回来的会是**本机**那一版，用户点"用服务器那一版替换"
就成了把笔记覆盖回自己的旧版。

`update_update`（引擎采纳对面那一版）也遵守同一条：引擎在取回字节做采纳的那一轮，把**同一份
字节**再登记到冲突行上（`ApplyOp::ConflictPayload`，只登记不改动正文）。所以界面不需要知道
冲突是哪一类，也没有"这一类可以回查本机历史"的例外分支。

留这一条是因为它真的错过一次：禁令当初只写在"卡片带了载荷"的分支上，没载荷时仍会去回查；
而单测把 `preview_text` 桩成抛错，"查失败所以空着"看起来完全正常，真界面里那次查询是成功的。
现在由 `scripts/verify-p11-panel.mjs`（真浏览器 + 两台真设备留在盘上的现场）钉住。

### 5.2 永久删除 vs 编辑

远端 `purged:true` 而本地有未上传的编辑 → 同样进收件箱，且**本地内容必须先完整保留**（写入冲突副本），再决定是否重建该笔记。永久删除的传播不能覆盖未同步的本地写入。

这一条现在有**两台真设备**的断言（`notera-host/tests/conflict_payload_e2e.rs::a_remote_purge_never_eats_an_edit_that_never_left_the_device`）：A 建 → B 拉到 → B 改但**一轮都不跑** → A 彻底删除并公告 → B 才同步。判据两条：B 的未裁决冲突里必须有这条，且那段从未上传的文字必须还读得回来（正文本身或卡片带来的副本）。**自证**：把 `plan.rs` 的 P13 从 `r.purged && !local_changed` 改成无条件 `r.purged`（也就是让永久删除真的盖掉未同步的本地写入）→ 这条测试当场红在"静默丢失"那句断言上，改回来就绿。之所以要这样验：`plan.rs` 的表头写着"永久删除传播优先于一切编辑"，光读代码会以为上面那条被推翻了 —— 判据的**前提**是"先留住"，两句话不矛盾，但没有这条测试就没人能证明实现记得这个前提。

### 5.3 反复活（协议层已保证，本文只列依赖点）

| 保证 | 出处 |
|---|---|
| 删除写进记录内容，不是删文件 | SYNC-PROTOCOL §8.2 |
| `tombstones` 不自动 GC | ADR-0006 |
| `missing_remote` 不导致本地删除 | SYNC-PROTOCOL §10 |
| 导出文件默认携带删除事实 | DATA-MODEL §15 |

因此"离线设备重新上线后把已删笔记传回来"需要同时违反以上四条，被结构性排除。

## 6. 冲突产物

自动合并失败时：

```text
原笔记 (note X)
  ├─ 内容 := 三方合并中"可无损确定的部分" ⊕ remote 版本
  ├─ rev := max(L.rev, R.rev) + 1
  └─ sync_conflicts 记录：base_rev, local_rev, remote_rev, local_hash, remote_hash,
                          conflicting_block_ids[], auto_merged=0, state='open'

冲突副本 (note Y, 新 id)
  ├─ 标题 := "<原标题> （来自 <设备名> · <本地时间>）"
  ├─ 内容 := 本地未合并版本（完整，逐字节保留）
  ├─ folder_id := 与 X 相同
  └─ 标记 origin='conflict_copy'，进入同一 outbox 上传
```

要点：

* **两条都在 UI 可见**，副本不是隐藏状态；
* 副本是普通笔记（可编辑、可删除、会同步）——不引入第二套数据模型；
* 原始内容逐字节保留，不做"清洗"；
* 副本自身参与后续同步，因此不会只在单机存在（换设备也能看到）。

### 6.1 为什么默认保留"远端为正文 + 本地为副本"

远端是**已被其他设备确认**的状态，本地是**尚未传播**的状态。把远端放正文、本地放副本，好处是：即使用户从不处理冲突，他看到的正文也是"别人已经在工作的那份"，而自己的那份以完整副本形式静静等待。反过来（本地为正文）会让设备间视图长期分裂，且用户更难发现"其实我覆盖过别人"。

这是可讨论的取舍，因此记入 ADR-0007 并在 §9 列为可回调项。

## 7. 用户可见层

冲突对用户只暴露一个入口，词汇表里不出现 "revision / merge / conflict copy"：

```
列表顶部出现一条柔和提示：  「1 条笔记有两个版本  ›」
点开 → 冲突收件箱卡片：
   标题 · 修改时间（本地/远端各一） · 左右并排预览（差异块高亮）
   三个按钮：保留两份（默认已做） / 用这个替换 / 我来合并
   「我来合并」→ 进入编辑态，两侧内容作为可复制区块并排展示
```

> **as-built（2026-09-27 对齐）**：示意图里的"列表顶部横幅"**没有实现**，实现的是两处更靠近对象的提示 ——
> ① 侧栏「需要处理的版本」入口带条数（`SidebarPanel.vue`），② **那条笔记自己的列表行上**画 ⚠
> （`list.contendedNote`，判据见 §5.1 第 4 步与 CF-15）。不补横幅的理由：同一件事说三遍不会让人更安心，
> 而横幅与行标记在"哪条有分歧"这句话上是重复的；如果 §51 更想要横幅，那是一个纯 UI 加法，不改语义。

* 默认动作是**已经安全的事**（两份都在），按钮只是"清理"，不是"必须决定才能继续用"。
  * as-built：`UpdateUpdate` 的"两份都在"由引擎当轮完成 —— 它取回远端记录并按 §6.1 采纳为正文，
    本机那份在采纳之前已存成副本笔记。因此卡片两栏的取法固定为：右 = **卡片自带的 `remotePreview`**
（唯一规则，见 §5.1.2 —— 这里原本写的是 `(noteId, remoteRev)`，那是 `UpdateUpdate` 采纳之后
才成立的特例形状；把它当通用规则留在文档里，会诱使下一个实现者把 P11 的右栏写成"回查本机
历史"，而那正是同一个缺陷被抓住两次的来源），
    左 = `(copyNoteId, copyRev)`（`ConflictDto.copyRev`）。"用我这一版"= 把正文与副本**互换**
    （两版各有一处存放，谁都没被吃掉；两条都重新公告），前提不成立时只关卡片、不动内容。两侧 `rev` 常常相等，所以**不许**两栏都按 `noteId` 取。
* 冲突不弹窗打断输入。
* 收件箱条目可"忽略"（保留两份，仅关闭提示），不丢内容。

| 钩子 | 用途 |
|---|---|
| `notera-richtext::merge(base, local, remote)` 纯函数 | L0/L1 属性测试：任意三方输入 → 输出必通过 validate；且 `merged` 包含两侧所有非冲突块 |
| ~~`NOTERA_SYNC_FORCE_CONFLICT=1`（test feature）~~ **未实现（2026-09-29 按实划掉）** | 全仓 `grep` 连一处 `env::var` 都没有。现在的做法是**真造分叉**：两台设备各写各的再各自同步（`conflict_payload_e2e.rs`、`sync_once.rs`），比开关可信 —— 开关会测到"我以为的分叉"，真设备测到"引擎真的这么判" |

**断言强度要求**：冲突用例的通过标准是"两份内容都能被逐字节找回"，不是"没有报错"或"笔记条数正确"。

# CONFLICT-RESOLUTION

Notera 的冲突检测、合并与删除语义。规范性文档。

关联：[SYNC-PROTOCOL.md](./SYNC-PROTOCOL.md) §7 判定表 · [DATA-MODEL.md](./DATA-MODEL.md) §4 revision / §10 富文本 · ADR-0005 / 0006 / 0007 / 0008

---

## 0. 唯一不可协商的目标

> **用户输入过的内容，不会因为同步、冲突、崩溃或另一台设备的操作而静默消失。**

冲突解决"不够聪明"是可以接受的（多留一份副本、多点一次按钮）；冲突解决"聪明到替用户做决定并丢掉一份内容"是不可接受的。本文所有规则都由此推导。

---

## 1. 什么才算冲突

### 1.1 判定式

```text
冲突 ⟺  L.rev ≠ L.sync_rev        （本地自上次一致点以来改过）
        ∧  R.rev ≠ L.sync_rev      （远端也改过）
        ∧  H(local) ≠ H(remote)    （最终内容确实不同）
```

`L.sync_rev` 是**双端确认过的共同祖先**（定义见 DATA-MODEL §4.3）。因此三方齐备：

| 输入 | 来源 |
|---|---|
| base | `note_revisions(note_id, rev = sync_rev).doc` |
| local | `notes.doc`（`rev = L.rev`） |
| remote | `records/note/<id>.json` 的 `payload` |

### 1.2 不算冲突的情形（必须显式排除，否则会产生大量假冲突）

| 情形 | 判定 | 依据 |
|---|---|---|
| 两侧最终内容相同（各自打开又保存、回环同步） | 收敛，`rev := R.rev` | SYNC-PROTOCOL P7 |
| 只有本地改 | Push | P5 |
| 只有远端改 | Pull | P6 |
| 仅 `pinned` / `color` 等标量属性不同 | 属性级合并（§4），不进冲突收件箱 | — |
| 仅 `folder_id` 不同且笔记正文一致 | 移动合并（§4.3） | — |
| 两侧改同一文档的**不同块** | 块级自动合并（§3） | — |
| 一侧改、另一侧删除 | **是**冲突（§5） | P11 |

### 1.3 禁止的判定方式

* 禁止用 `updated_at` / mtime / 服务器时间比较新旧（时钟不可信，R3）。
* 禁止"整篇文档二选一"作为默认策略。
* 禁止用"远端文件不存在"推断"用户删了它"（SYNC-PROTOCOL §10）。

## 2. 合并流水线

```text
检测冲突
  ↓
① 信封级：kind/id 一致？协议版本支持？            否 → 只读 + 上报
  ↓
② 文档级：H(local) == H(remote)？                  是 → 收敛，结束
  ↓
③ 块级三方合并（§3）                               成功 → AutoMerged，记 auto_merged=1
  ↓
④ 标量属性合并（§4）
  ↓
⑤ 仍有无法判定的块                                 → 生成冲突记录 + 冲突副本（§6）
```

第 ③ 步成功时**不产生任何用户可见的冲突提示**，只在 `sync_conflicts` 留一条 `auto_merged=1` 的记录供审计。这是"用户不该感知同步系统"（§2 产品目标）的落点。

## 3. 块级三方合并

### 3.1 为什么按块而不是按字符

富文本模型（DATA-MODEL §10）保证**每个顶层块有稳定 `id`**，跨编辑不漂移。于是：

* 两人在同一段落各写一句 → 同 id 块两侧都改 → 块级冲突；
* 两人各写不同段落 / 一个改正文一个加图片 → 不同 id → 无损自动合并。

按字符做 diff（Myers 之类）在这里是**更弱**的方案：段落顺序漂移会让"同一段"对不齐，从而把可合并的场景误判为冲突。块 id 是应用自己维护的锚点，比文本相似度可靠。

### 3.2 算法（纯函数，`notera-richtext::merge`）

```text
输入 base, local, remote（均 normalize 过）
1. 建 id → block 映射；记录三方的顶层块顺序
2. 对每个 base 块 b：
   a. b 不在 local 且不在 remote          → 删除（无争议）
   b. b 不在 local 但 H 未变于 remote     → 采纳删除
   c. b 不在 remote 但 local 保留         → 保留 local（视为 local 未删）
   d. 两侧都在：
      - H(local_b)==H(base_b) → 取 remote_b
      - H(remote_b)==H(base_b) → 取 local_b
      - 两侧都改且 H 相等       → 取任一
      - 两侧都改且 H 不等       → 冲突块，进 §3.3 处理
3. 新增块（不在 base）：local-only / remote-only 都并入；
   两侧各加了一个内容相同的新块（同文本不同 id）→ 去重保留一个
4. 顺序：以 base 顺序为骨架插入；两侧都调整了顺序 → 顺序判为冲突
5. 输出 MergeOutcome
```

### 3.3 冲突块的降级顺序（依次尝试，任一成功即止）

| 级 | 条件 | 结果 |
|---|---|---|
| M1 | 一侧只是格式变化（`plain_text` 相同，marks/attrs 不同） | 采纳带格式的一侧，另一侧格式丢弃但记入审计 |
| M2 | 一侧是另一代的严格超集（`base ⊂ local ⊂ remote` 逐字符包含） | 采纳超集侧 |
| M3 | 两侧都是对 base 的纯追加（前缀相同） | 拼接两侧追加内容 |
| M4 | checklist 项：一侧勾选、一侧改文本 | 文本取改动侧，勾选状态取改动侧，冲突则默认未勾选并保留另一状态到 `unknown_attrs` |
| M5 | 以上都不成立 | **该块判冲突**，整篇走 §6 |

M1–M4 都是"能证明无损"才做，不是"看起来差不多"。合并结果必须满足：`H(merged) ≠ H(base)` 且 merged 包含两侧所有可辨识内容。

### 3.4 失败保护

自动合并产出的文档必须重新 `validate()` + `normalize()`；不通过则**丢弃合并结果**，退回 §6 保留双方。绝不写回一个未通过校验的文档。

## 4. 标量属性与结构字段合并

| 字段 | 规则 |
|---|---|
| `pinned` | OR（一侧固定即固定）；两侧都从 true 变 false 才为 false |
| `color` | 一侧为 null 取另一侧；都非 null 且不同 → 取 remote，local 值记入审计（不升级为冲突） |
| `name`（文件夹） | 两侧都改且不同 → 取 remote，local 值记审计并提示；文件夹不做冲突副本（副本文件夹会污染侧栏） |
| `folder_id`（笔记移动） | 一侧移动一侧未动 → 采纳移动；两侧移到不同文件夹 → 采纳 remote，记审计 |
| 文件夹 `parent_id` | 两侧都改 → 采纳 remote，并检测环；成环则整体回退到 base 父级并记诊断 |
| `deleted_at` | 见 §5 |
| `attachments` 引用 | 并集（引用是内容的一部分，不因删除引用而丢 blob） |

原则：**属性冲突降级为"审计 + 提示"，内容冲突才升级为"收件箱 + 副本"**。用户不会为颜色产生挫败感，但会为丢字产生。

## 5. 删除语义（三处易错点）

### 5.1 删除 vs 修改（P11）

```text
设备 A：编辑笔记（rev 7→8）
设备 B：删除同一笔记（rev 7→8, deleted_at=T）
```

协议上两侧 `rev` 都大于 `sync_rev=7` → 真冲突。处置：

1. **保留内容**（数据安全 > 一切）：合并后笔记存活，`deleted_at=NULL`；
2. 写 `sync_conflicts(kind=delete_vs_edit)`；
3. UI 冲突收件箱给出两个明确动作：**"仍要删除"**（→ 永久删除流程，`rev` 再 +1 传播）或**"保留这份修改"**；
4. 在用户选择前，笔记显示在正常列表并带"⚠ 其他设备删除了这条"标记。

不做"谁的时间晚听谁的"——那等于允许一台误删的设备吃掉另一台的编辑成果。

### 5.2 永久删除 vs 编辑

远端 `purged:true` 而本地有未上传的编辑 → 同样进收件箱，且**本地内容必须先完整保留**（写入冲突副本），再决定是否重建该笔记。永久删除的传播不能覆盖未同步的本地写入。

### 5.3 反复活（协议层已保证，本文只列依赖点）

| 保证 | 出处 |
|---|---|
| 删除写进记录内容，不是删文件 | SYNC-PROTOCOL §8.2 |
| `tombstones` 不自动 GC | ADR-0006 |
| `missing_remote` 不导致本地删除 | SYNC-PROTOCOL §10 |
| 导出文件默认携带删除事实 | DATA-MODEL §15 |

因此"离线设备重新上线后把已删笔记传回来"需要同时违反以上四条，被结构性排除。

## 6. 冲突产物

自动合并失败时：

```text
原笔记 (note X)
  ├─ 内容 := 三方合并中"可无损确定的部分" ⊕ remote 版本
  ├─ rev := max(L.rev, R.rev) + 1
  └─ sync_conflicts 记录：base_rev, local_rev, remote_rev, local_hash, remote_hash,
                          conflicting_block_ids[], auto_merged=0, state='open'

冲突副本 (note Y, 新 id)
  ├─ 标题 := "<原标题> （来自 <设备名> · <本地时间>）"
  ├─ 内容 := 本地未合并版本（完整，逐字节保留）
  ├─ folder_id := 与 X 相同
  └─ 标记 origin='conflict_copy'，进入同一 outbox 上传
```

要点：

* **两条都在 UI 可见**，副本不是隐藏状态；
* 副本是普通笔记（可编辑、可删除、会同步）——不引入第二套数据模型；
* 原始内容逐字节保留，不做"清洗"；
* 副本自身参与后续同步，因此不会只在单机存在（换设备也能看到）。

### 6.1 为什么默认保留"远端为正文 + 本地为副本"

远端是**已被其他设备确认**的状态，本地是**尚未传播**的状态。把远端放正文、本地放副本，好处是：即使用户从不处理冲突，他看到的正文也是"别人已经在工作的那份"，而自己的那份以完整副本形式静静等待。反过来（本地为正文）会让设备间视图长期分裂，且用户更难发现"其实我覆盖过别人"。

这是可讨论的取舍，因此记入 ADR-0007 并在 §9 列为可回调项。

## 7. 用户可见层

冲突对用户只暴露一个入口，词汇表里不出现 "revision / merge / conflict copy"：

```
列表顶部出现一条柔和提示：  「1 条笔记有两个版本  ›」
点开 → 冲突收件箱卡片：
   标题 · 修改时间（本地/远端各一） · 左右并排预览（差异块高亮）
   三个按钮：保留两份（默认已做） / 用这个替换 / 我来合并
   「我来合并」→ 进入编辑态，两侧内容作为可复制区块并排展示
```

* 默认动作是**已经安全的事**（两份都在），按钮只是"清理"，不是"必须决定才能继续用"。
* 冲突不弹窗打断输入。
* 收件箱条目可"忽略"（保留两份，仅关闭提示），不丢内容。

## 8. 可测性与测试钩子

| 钩子 | 用途 |
|---|---|
| `notera-richtext::merge(base, local, remote)` 纯函数 | L0/L1 属性测试：任意三方输入 → 输出必通过 validate；且 `merged` 包含两侧所有非冲突块 |
| `NOTERA_SYNC_FORCE_CONFLICT=1`（test feature） | 强制把远端 rev 视为已分叉，用于稳定复现冲突路径 |
| `notera-cli sync-once --scenario <toml>` | L3 多设备 E2E 构造 A/B 并发编辑 |
| `sync_conflicts` 表 + `DUMP` 服务端快照 | 断言"两份内容都在"（内容哈希级，而非条数） |

必须存在的用例（TEST-PLAN.md 同步矩阵已列）：同块并发、异块并发（应自动合并且**不**提示）、删除 vs 修改、修改 vs 删除、格式 vs 文本、checklist 并发、两侧移动、离线一周后汇合、三方（A/B/C 同时改）。

**断言强度要求**：冲突用例的通过标准是"两份内容都能被逐字节找回"，不是"没有报错"或"笔记条数正确"。

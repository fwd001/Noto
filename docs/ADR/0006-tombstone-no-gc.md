# ADR-0006: 删除与墓碑（不自动 GC，文件夹不级联）

## 状态
日期：2026-09-25
状态：Accepted

## 背景
需求明令禁止"删除后因为同步而重新出现"。这条路径之所以常见，正是因为多数实现把删除实现为"文件消失"：A 删 → 服务器文件不见 → B 的本地缓存重新上传 → 笔记复活。要结构性排除它，删除必须是**可传播的记录内容**。

## 决策
- 删除是记录内容（信封的 `deleted_at` 字段），不是"文件消失"；服务器上的记录仍在，只是带着删除事实。因此删除与编辑共用同一条已验证的 `Push` 路径。
- `tombstones` 表**不自动 GC**：本地即使物理删了行，删除事实仍在，重新拉取时不会被当作"本地新增"。
- 永久删除以 `purged:true` 的空载荷记录传播，接收方写 `tombstones(purged=1)` 并删除本地行。
- **文件夹删除不级联删除笔记**：只写文件夹自己的墓碑，子文件夹上移一级、笔记移入默认本（P15）。
- 远端缺失（404）永不导致本地删除，只导致补传（C2）：连续 3 轮 404 → 标 dirty 走 `missing_remote`（P3）。
- 清单大面积背离需人工确认（C3/D3），不得翻译成"用户删了几千条"。

## 备选方案与被否决的原因
- 墓碑 TTL 30/90 天自动清理：离线超过 TTL 的设备必然复活已删笔记，与硬性禁令直接冲突；且"多久算超过"无法向用户解释。
- 级联删除并生成 N 条墓碑：一次误触摧毁整个子树的内容；同时删除变成最重的操作（N 条墓碑 + N 次远端写，还会挤满单轮预算）。
- 依赖服务器回收站：服务器回收站的语义不受我们控制（是否可被服务端恢复、是否参与 PROPFIND、保留多久均不确定），且删除事实无法跨设备传播。见 SYNC-PROTOCOL §16 U7。

## 后果
正面：复活需要同时违反"删除是内容 / 墓碑不 GC / 404 不删本地"三条，被结构性排除；删除是普通写，崩溃点矩阵与幂等机制自动覆盖它。
代价：
- 墓碑条目永久累积：每条约 100–200 B，1 万条删除约 2 MB，且参与清单与分段计算（读端要为墓碑多留路径）。
- 必须提供显式的"压缩远端"维护动作作为出口，该动作本身要能诊断、要人工触发、要有预览。
- 文件夹删除不级联会让用户以为"删了文件夹就删了里面东西"，需要 UI 明确显示"内含 N 篇笔记将移入默认本"。

## 验证方式
- 反复活专项用例：A 删除笔记 N → 同步 → B 离线 30 天（fake clock 推进）→ B 上线同步 → 断言 B **不上传** N（`STATS` 中无 `PUT records/.../<N>.json`），且三方条目数一致（TEST-PLAN FT-NOTE-05/06、MD-*）。
- `missing_remote` 用例：直接 `DELETE records/n/<id>.json` 而清单仍引用 → `A sync` 断言本地行数不减、该实体标 dirty 并补传（SY-INT-02、INV-03）。
- 文件夹删除用例：F 含 3 篇笔记 → 删除 F → 断言笔记计数不变（3 篇全部可见、移入默认本）、`tombstones` 只新增 1 条、远端 `PUT` 次数 = 1（文件夹自身）。
- 永久删除传播：A `purged:true` → B 同步后本地无该行且 `tombstones(purged=1)` 存在；再跑一轮 no-op，断言 B 不重新上传（INV-02/11）。

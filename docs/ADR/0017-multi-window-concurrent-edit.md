# ADR-0017: 多窗口并发编辑同一条笔记（未决）

## 状态
日期：2026-09-25
状态：**Proposed**（问题记录 + 倾向，Phase 4 决策）

## 背景
macOS 与 Windows 支持多窗口（PLATFORM.md §7 记明"每条笔记可弹出独立窗口编辑"），因此可能出现两个窗口编辑同一条笔记。这与"两台设备编辑同一条"在协议上是同一形状：同一 `rev` 起点、两份未传播的本地修改。区别只在于用户预期——同一台机器上自己和自己冲突，很难解释。

当前保护已存在：命令层（`notera-host::commands`）带 `expectedRev` 乐观并发检查，`expectedRev` 与库内 `rev` 不匹配即返回冲突并让 UI 重载，因此不存在"后保存的窗口静默覆盖先保存的窗口"这条路。本 ADR 要决定的不是安全性，而是产品形态。

## 决策
本 ADR 不做最终决定，只固定评估口径并记录倾向：
- 判据 1：任何选项都不得放松 `expectedRev` 检查（它是本机与跨设备共用的唯一闸门）。
- 判据 2：不得引入第二套"窗口间"冲突语义——冲突只有一条路径（ADR-0007）。
- 判据 3：用户在同一台机器上不应看到"来自本机自己"的冲突副本，除非有明确解释文案。
- 倾向：选项 ①（v1 禁止同一笔记开两个可编辑窗口）。Phase 4 结合窗口管理实现进度确定。

## 备选方案与被否决的原因
- ① v1 禁止同一笔记开两个可编辑窗口（第二窗口以只读打开，或聚焦已有窗口）：最简单，冲突面直接归零。代价是体验——多窗口的用途常常正是"两篇对照"，限制同一篇会显得苛刻；且需要窗口注册表来跟踪哪条笔记在哪个窗口。
- ② 允许多窗口 + 冲突副本：复用 ADR-0007 的同一条路径，无新增协议代码。代价是本机自己产生冲突副本，用户会困惑"我不过是在两个窗口里改同一篇"，并需要额外的解释文案。
- ③ 允许多窗口 + 实时同步编辑态：**否决** —— 需要在会话内引入 CRDT 或操作广播（并处理窗口关闭/崩溃后的会话清理），与 ADR-0007 对 CRDT 的否决理由一致，代价远超收益，且实时协同与"本地写入即时提交"的模型相互牵制。

## 后果
正面：问题、判据与倾向被写进文档，Phase 4 做窗口管理时不会临时发明第三种语义；当前已有的 `expectedRev` 保护被明确列为不可放松项。
代价：
- 这是一个开放项：Phase 1–3 期间任何窗口管理代码都要保持"两个可编辑窗口同时存在时数据仍安全"这一底线，即使产品尚未决定允许它。
- 倾向 ① 会引入窗口注册表（哪条笔记在哪个窗口、什么状态），这块成本在 ①② 两个选项下都要付（②只是付完之后还多付冲突文案）。

## 验证方式
- 无论选哪个方案，必须存在的用例：同一笔记在两个窗口/两个 `notera-cli` 会话中各自编辑并保存 → 断言后写入者收到冲突返回、库中保留两份内容（原笔记 + 冲突副本或明确的拒绝写入），**不存在静默覆盖**（INV-01）。
- 若采纳 ①：断言第二窗口只读（编辑控件不可交互、无 PUT/写事务发出），并有可理解的提示文案；`expectedRev` 检查不得因"同机同用户"被绕过（grep 闸门禁止以窗口 id 为由跳过该检查）。
- 若采纳 ②：断言冲突副本标题含设备与时间且指向本机，UI 文案在收件箱内可见；副本总数 ≤ 冲突数（不随保存次数线性增长）。
- 决策时点：Phase 4 出口条件里加一条"本 ADR 状态改为 Accepted 或 Superseded，且 PLATFORM.md P4 关闭"。

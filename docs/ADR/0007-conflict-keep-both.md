# ADR-0007: 冲突解决（块级三方合并，失败保留双方）

## 状态
日期：2026-09-25
状态：Accepted

## 背景
唯一不可协商的目标：用户输入过的内容不会因同步、冲突、崩溃或另一台设备的操作而静默消失。合并"不够聪明"可以接受（多留一份副本、多点一次按钮）；合并"聪明到替用户做决定并丢掉一份内容"不可接受。因此冲突策略的取向是确定的，剩下的只是把代价放在哪。

## 决策
- 先做**块级三方合并**：富文本每个顶层块有稳定 `id`（ADR-0008），作为合并锚点；base 取自 `note_revisions(rev = sync_rev)`。
- 可无损合并则**静默收敛**：不弹提示，只在 `sync_conflicts` 记一条 `auto_merged=1` 供审计。
- 降级顺序（每一级都要求"能证明无损"，不是"看起来差不多"）：
  - M1 一侧只是格式变化（`plain_text` 相同）→ 采纳带格式侧
  - M2 一侧是另一侧的严格超集 → 采纳超集侧
  - M3 两侧都是对 base 的纯追加 → 拼接
  - M4 checklist 勾选 vs 文本 → 各取改动侧，冲突则默认未勾选并保留另一状态
  - M5 以上都不成立 → 判冲突
- 合并失败则**保留双方**：原笔记取远端为正文，本地完整内容生成"冲突副本"（普通笔记，标题带设备与时间），并写入 `sync_conflicts` 收件箱。
- 属性 / 标量冲突（`pinned`、`color`、`folder_id` 等）降级为"审计 + 提示"，不升级为收件箱。
- 删除 vs 修改（P11）必进收件箱，且本地内容先完整保留。

## 备选方案与被否决的原因
- 整篇二选一（本地胜 / 远端胜）：静默丢内容，违反唯一目标；按"谁的时间晚听谁的"实现还额外依赖不可信时钟。
- 字符级三方 diff（Myers 等）：段落漂移会把"两侧各写不同段落"这种可合并场景误判为冲突，且合并结果在可读性上不可控；块 id 锚点比文本相似度可靠。
- CRDT（Yjs / Loro）：需要常驻合并状态与历史同步，与"离线任意久之后汇合"以及 WebDAV 文件形态不匹配，代价远超收益；保留为未来的可选层，不进 v1 协议。

## 后果
正面：内容冲突的最坏结果是"多一份副本"，不是"少一份内容"；自动合并覆盖常见并发写作（不同段落、格式 vs 文本、纯追加）。
代价：
- 极端情况下用户会看到冲突副本，需要手动清理；`sync_conflicts` 收件箱是一个必须做好 UI 的额外界面。
- 合并器是协议的一部分：`merge()` 的输出必须过 `validate()`，否则丢弃合并结果退回保留双方——多一条永不豁免的失败路径。
- 默认取向（远端为正文、本地为副本）是主观取舍，已在 CONFLICT-RESOLUTION §6.1 说明并列为可回调项（其 C1）。

## 验证方式
- 通过标准是"两份内容都能**逐字节**找回"，不是"无报错"或"条数正确"（TEST-PLAN 断言强度要求）：断言两份正文 hash 分别等于 A、B 版本。
- 属性测试：对任意三方输入，`merge()` 输出必过 `validate()`，且 `merged` 包含两侧所有非冲突块（`notera-richtext::tests`）。
- 必覆盖用例：同块并发（SY-CONF-01）、异块并发（SY-CONF-02，断言**不产**副本）、格式 vs 文本、两侧移动（FT-MOVE-02）、checklist 并发（FT-CHK-02）、删除 vs 修改（SY-CONF-04）、三方 A-B-C 同时改（MD-01/03）、离线一周后汇合（MD-03）。
- 不动点断言：冲突处理完再跑一轮 no-op，条目数与 manifest hash 不变（副本不是每次同步都会再产生一份）。

# ADR-0004: 清单两段式（基线分段 ⊕ 变更窗口）

## 状态
日期：2026-09-25
状态：Accepted

## 背景
清单是每轮同步的入口。若"每轮重写全量清单"，5000 条笔记的每一次编辑都要上传 186 KiB gzip——空轮与轻改动轮的流量与库规模挂钩，内网与移动网络都不可接受。尺寸不是估算，是实测。

实测尺寸（条目 `{i,r,h,s,t}`，`docs/evidence/` 尺寸测量，见 SYNC-PROTOCOL §4.2）：

| 形态 | 裸大小 | gzip |
|---|---|---|
| 单条目 | 89 B | — |
| 全量 5000 条 | 438.7 KiB | 186 KiB |
| 全量 20000 条 | 1 754 KiB | 742 KiB |
| 窗口 200 条 | 17.7 KiB | 7.8 KiB |
| 分段 2000 条 | 175.6 KiB | 74.7 KiB |

## 决策
- `manifest/index.json` 携带三样东西：`seq`、分段目录（`segments[]`，每段 ≈2000 条）、最近 200 条变更窗口（`window.entries`）。
- **有效远端状态 = 所有分段条目，被窗口条目覆盖（窗口优先）。**
- 压实（compaction）仅在以下任一条件触发：`window.entries.len > 200`；窗口与某分段的 id 重叠率 > 20%；`seq` 距上次压实 > 5000。
- `checksum` = 去掉 `checksum` 自身字段后的 canonical JSON 的 sha256（自校验，防半写与截断）。
- 保留 `manifest/index.json.prev`，作为损坏回退的第一级。
- 损坏恢复阶梯（严格顺序，任一级成功即停）：D1 读 `prev` → D2 `PROPFIND` 扫描 `records/` 从记录重建 → D3 背离 > 30% 且 > 50 条则**要求人工确认**，拒绝据此删本地 → D4 单分段 checksum 不符只丢弃该分段缓存。

## 备选方案与被否决的原因
- 全量单文件清单：见上表实测，每轮重写成本与库规模同阶，直接否决。
- 只靠 `PROPFIND` 不用清单：万级文件下列举请求数与延迟不可接受，且拿不到 `rev`/`hash` 之外的语义（还得逐个 HEAD）。
- 按 id 前缀静态分桶：UUIDv7 时间有序，新数据全落在少数桶里形成热桶，每轮仍要重写大桶；且压实语义比"分段 + 窗口"更复杂。

## 后果
正面：每轮成本与库规模解耦——空轮 1 请求 0 字节，改动轮上行窗口 ≈7.8 KiB 量级；清单损坏有确定阶梯。
代价：
- 读端要实现三档成本路径（无变化 / 落后 ≤ 窗口 / 落后 > 窗口 / 全新设备）与压实触发器，复杂度集中在 `notera-sync::manifest` 一处。
- 压实是唯一重写分段内容的动作，它自身也要走 CAS 与崩溃点判定（C10）。
- `hash12` 截断（12 hex）只作快速路径提示，权威判定仍需记录内全量哈希，读端不能省这一步。

## 验证方式
- L3 `STATS` 断言空轮 = 1 请求 / 0 字节（manifest 返回 304），任何"每轮下载全量清单"的实现即失败。
- 每轮预算断言：本地改 1 条笔记 → ≤ 4 请求、上行 ≤ 9 KiB（记录 ≈1 KiB + 窗口 ≈8 KiB）。
- 人为 `FAIL(corrupt-body,target=.notes/manifest/index.json)` 后必须走 D1 回退 `prev`，且**不清空本地**（断言本地条目数与 hash 不变）。
- D3 闸门用例：`DUMP` 删除 > 30% 且 > 50 条记录后同步，断言进入 `phase=error` 等待人工确认，无本地删除。
- 压实回归：窗口 > 200 条后一轮内窗口归零、受影响分段 hash 变化、条目数守恒。

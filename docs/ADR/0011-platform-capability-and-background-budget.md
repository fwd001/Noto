# ADR-0011: 平台能力抽象与后台同步诚实预算

## 状态
日期：2026-09-25
状态：Accepted

## 背景
共享核心 + 平台原生能力是既定路线（ADR-0001），但"原生差异"必须以何种形式进入代码是未决的：按机型分支会在四端 × N 版本下失控。同时移动端后台执行受系统调度约束，把系统能力当成应用线程来承诺，写出来的只能是假话。

## 决策
- 能力用 `PlatformCaps` + capability trait 声明（`Lifecycle` `BackgroundTask` `Notifications` `Tray` `GlobalShortcut` `FilePicker` `Share` `NetworkMonitor` `Secrets` `SystemTheme`）；UI 按能力渲染，**禁止按机型分支**——正确写法是"因为 `caps.tray == false` 所以不渲染托盘入口"，不是"因为是 iPhone 所以"。
- 能力缺失必须显式降级：`bg_task == None` 时不显示"后台自动同步"开关，而不是显示一个不工作的开关。
- 定时预算：
  - 桌面：保存 debounce 2.5 s + **周期 25 s**（给一轮留 5 s 余量，才能兑现 ≤30 s 到达另一台设备；空轮 1 请求 0 字节使 25 s 轮询不构成负担）。
  - 移动：主路径 WorkManager / BGAppRefreshTask，系统最小约 15 min 且**不保证执行**；iOS 后台时间片约 30 s 量级。
- **明确不承诺移动端 30 s 到达**。真实承诺是"打开设备时已同步"（加上桌面之间 ≤30 s）。
- 后台时间片内禁止发起大 relist / 大附件，优先 ETag 304 快路径。
- 移动进入后台：停止发起新轮，当前轮在 5 s 内收尾，未完成留下轮。

## 备选方案与被否决的原因
- 承诺移动端 30 s：把系统调度当应用线程，做不到还得伪装做到；测试矩阵与产品文案会一起变成假的。
- 常驻前台服务保活（Android）：耗电、易被系统杀、商店策略风险，且 iOS 无对应能力——四端一致性反而被破坏。
- 服务端推送唤醒：WebDAV 没有推送通道，需要额外服务器与账号体系，违背"数据由用户掌控"的最小部署前提。

## 后果
正面：平台差异被关在 `platform/*` 与能力协商里（P2），领域层不知道机型；同步时效有可测口径，产品文案可如实写。
代价：
- 移动端同步时效真实弱于桌面，用户可能质疑"为什么手机上不是立刻同步"，需要文案承担而不是实现去掩盖。
- `PlatformCaps` 是一层额外抽象，每个能力的四端实现与降级路径都要单独测。
- 后台时间片约束使"一轮必须能在 30 s 内完成"成为设计约束，限制了后台可做的事（大 relist 只能挪到前台）。

## 验证方式
- 桌面端到端延迟实测：A 改 → B 见 ≤30 s（PERF-08），L3 时间戳 + L5 真机复核。
- 移动用例断言：冷启动后 3 s 内完成一轮 pull（L6 平台冒烟：起进程 → 打开 SQLite → 完成一轮 sync）。
- 能力矩阵一致性测试：对 `caps` 的每种组合断言 UI 入口集合，`caps.tray == false` 时 DOM 中不存在托盘设置入口；`bg_task == None` 时不存在后台自动同步开关。
- 后台收尾断言：注入"进入后台"事件后，`STATS` 中不再出现新的 `GET manifest` 请求，且当前轮在 5 s 内结束（未结束项留下轮）。
- grep 闸门：`apps/desktop/src` 与 `notera-host` 中不出现按机型/平台名的条件分支（平台名只允许出现在 `platform/*`）。

# ADR-0021: rev 口径补齐 —— 远端头部要真的进得来，冲突产物要真的 `max+1`

## 状态
日期：2026-09-29
状态：Accepted。**D1 = 0.0.35 已落地并验通；D2（含按实新增的 P14）= 0.0.36 已落地并验通；D3 仍未做**（见"按实落地"一节）
关联缺陷：`PRODUCTION-READINESS` §7 的 **G17**（两侧 rev 撞车那一行永远追不平）与 **G18**（同名本地副本一篇一篇累积）
判据：`TEST-PLAN` 的 **P11-SR-01**（两台真设备）、新增 **SY-REV-01**

## 背景

两条**文档早就写了、代码从来没有执行**的编号规则，在这次两台真设备的实验里同时暴露：

1. **DATA-MODEL §0 的 I2** 写的是 `rev = max(rev, remote_rev) + 1`，`notera_core::next_rev`
   的注释更是直接承诺"这样即使两台设备离线并发编辑，编号也不会相等"。
   但 `commit_edit`/`move_folder`/`purge` 全部把 `cur.note.remote_rev` 当作"已观测到的远端头部"
   （`store.rs:901`、`store.rs:1040`、`store.rs:379`），而**这一列在生产里永远是 0**：
   引擎只发 `ApplyOp::SetRemote{kind:"manifest"/"seq"}`（`sync/lib.rs:968`、`sync/lib.rs:1020`），
   到 host 的映射处 `EntityKind::from_tag("manifest")` 给 `None` 就被丢掉（`host/lib.rs:3180`），
   `StoreApplyOp::SetRemote` 对 note/folder **零个生产调用点**（`set_remote_rev` 只有测试在调）。
   于是 `next_rev(local, Rev(0))` 恒等于 `local + 1` —— 注释里那句"编号不会相等"是个没兑现的许诺。

2. **CONFLICT-RESOLUTION §6** 写的是冲突产物 `rev := max(L.rev, R.rev) + 1`。
   代码里裁决只动卡片那一行（`host/lib.rs:866-941`，`keepBoth` 走到 `store.resolve_conflict` 为止），
   **没有任何一处把"本机那一版"抬到对面之上再发出去**。

两条叠在一起的可观测后果（`crates/notera-host/tests/p11_same_rev.rs` 实测，两台真设备 + 真 TCP WebDAV）：
A 删除（rev 1→2）与 B 编辑（rev 1→2）互不知情 → 服务器记到的是 rev 2 的**删除**，
B 那一版停在 `rev=2 / sync_rev=1 / 脏=true`，而 `apply` 明令拒绝"同 rev 不同内容"
（`apply.rs:308-323`，那道闸门本身是对的，防的是服务器侧异常）——
**这一行永远发不出去，设置页"待处理任务"从此永远 ≥1**；
卡片是按当前分叉每轮重算的（`sync/lib.rs:623` 重新 `Plan::build`），所以裁决过的卡片又回到收件箱（G17）；
而 §6 那份"进收件箱同时留一份本地副本"是按**卡片**去重的，卡片回来一张就多一篇副本，
实测 1 → 2 → 3（G18）。

## 决策

**不新造编号机制，只把已经写进文档的两条规则接上，并给它们各自一条能红的门禁。**

### D1 远端头部要进得来（喂 `remote_rev`，单调）

每轮同步拿到远端视图时，host 已经把整份视图灌进 `sync_remote_index`
（`host/lib.rs:3065` → `remote_index_replace`）。就在同一个事务点旁边，把同一批 `rows` 里
note/folder 的 rev **单调地**写回实体行的 `remote_rev`：

```sql
UPDATE notes SET remote_rev = MAX(remote_rev, ?rev) WHERE id = ?id
```

* 单调（`MAX`）而不是覆盖：这一列的语义是"本机**见过**的远端最高编号"，回退它会让 I2 失效。
* 只写 `remote_rev`，**不动 `sync_rev`**：`sync_rev` 是三方合并的 base，动它等于改写共同祖先（DATA-MODEL §4.3）。
* 附件不在这一批里（`set_remote_rev_tx` 对附件本来就是 `Err`：sha256 寻址）。
* 效果：B 只要**观测过**对面更高的一版，它下一次本地编辑就必然落在对面之上（`max+1`），
  推得出去、结得清账。这消灭的是"能观测却仍然撞车"那一大类。

### D2 冲突产物真的拿 `max+1`

裁决时，凡是**用户决定让本机那一版继续存在**的动作（`keepBoth`，以及"保留本地/我来合并"之后
仍留在本机那一条未公告的头），在同一次事务里：

1. `rev := max(本地头, 已观测远端头) + 1`（走 `next_rev`，不许手写 `+1`，与 store.rs 顶部那条规矩一致）；
2. 该行的 `note_revisions` 里 rev 为撞车号那一条**保留**（§4.4：`rev >= sync_rev` 的版本不许删），
   新版本另插一行；
3. 用新 rev 重新入队上写（`enqueue` 的去重键含 rev，所以旧那一行必须一起 `supersede_up_to` 结掉，
   否则 `outbox_pending` 虚高、"待处理任务"数字仍然不掉）；
4. 之后走已验证的 Push 路径，服务器那道 `want.rev <= m.rev` 的闸门（`client.rs:643`）自然放行。

`apply.rs` 那条"同 rev 不同内容"的拒绝**保持原样、不许放宽**，`adopt` 也不扩大到 P11：
把对面正文盖到撞车的同一个编号上，等于改写双方共同认为存在的那一版（§5.1 禁"静默二选一"）。

### D3 引擎不许再静默吞掉 apply 的拒绝

`sync/lib.rs:758-766` 那句 `.unwrap_or_default()` 与十几处 `let _ =` 把拒绝文本直接扔掉。
本决定只要求**最小的一条**：本地 apply 返回 `Err` 时，把实体与原因落进已有的
`sync_state.last_error_code/last_error_at` 那一格并让 `SyncEvent::Failed` 有对应 message_key ——
拒绝必须有去处，具体文案属界面层，不在本 ADR 定。

## 备选方案与被否决的原因

* **裁决时直接采纳对面正文并覆盖同一个 rev（放宽 `adopt`）** —— 否决：改写双方共同祖先那一版，
  是"静默覆盖用户数据"那条硬禁止的邻域；而且覆盖之后 `sync_rev` 与 base 关系要重定义。
* **让 P11 在规划阶段就改走 Push（把冲突判定往后挪）** —— 否决：P11 排在 P5 之前是刻意的
  （`plan.rs:169`），先问用户再动服务器；把顺序倒过来等于用"能推出去"换掉"不替用户决定"。
* **给 outbox 做一个真正的队列消费者（`outbox_take`）** —— 否决：`outbox_take` 至今没有生产调用点，
  造队列消费者是另一台状态机（§39 禁重复状态机），而且不解决编号撞车这个根因。
* **不修，让 G17 挂着** —— 否决过一次：它不是"账不好看"，B 那一版**永远发不出去**，
  用户必须再编辑一次才能自救，而"再编辑"会把刚裁决过的副本又留一遍（G18）。

## 后果

* **正面**：§1.2/§6/I2 那三句从"描述了一个不存在的动作"变成真的；G17 的两半（账结不掉 + 卡片回来）
  与 G18 的累积同源消解 —— 分叉一旦能被公告，卡片不再重算出来，副本也就没有第二篇。
* **风险（逐条对着代码列，实现时每条都要有数）**：
  1. `mark_synced` 拒绝 `rev > 本地头部`（`syncml.rs:509-513`）→ 抬号必须先改行再入队，否则 `dirty` 永远挂着；
  2. `note_revisions` 以 `(note_id, rev)` 为键且 `ON CONFLICT DO UPDATE`（`rows.rs:454-471`）→ 抬号是新行，
     撞车号那一版必须留着当 base；
  3. 服务器闸门是 `<=` 不是 `<` → 抬号必须**严格大于**对面记录的那一版；
  4. 后续拉取时 `apply` 的 I2（`apply.rs:302-307`）会拒 `env.rev < 本地头部` → 规划只在 `r.rev > l.rev` 时发 Pull，
     抬号不会把合法的 Pull 挡掉，但**这条推理由判据来钉**，不靠推理；
  5. 租约（`sync/lib.rs:901-929`）可以推迟公告 → 抬号后没公告，落在已有的 C4 窗口语义里，不新增状态；
  6. 清单压实与窗口增长（`compact_if_needed`）→ 每次裁决多一条版本记录，量级是"用户点一次按钮"，可接受；
  7. 哈希口径：短 12 位 vs 全哈希（`same_content_hash`）→ 任何新比较都走这个函数，不许自己截。
* **分两批落地（每批各自带门禁、各自提交）**：
  批一 = D1（观测得到的那一类）；批二 = D2 + D3（撞车之后的账），并把 `patches/p11-same-rev-stall.patch`
  里那两条会红的断言**升进主干**，补丁退役。

## 按实落地（2026-09-29，批二 = 0.0.36）

D1 与 D2 **已实现并验通**；D3 没做（`sync/lib.rs:758-766` 那句 `.unwrap_or_default()` 仍在，
账本批已经不靠它暴露，但"拒绝要有去处"这条独立要求还欠着）。

**落地时比本 ADR 原来写的多了一条规则，这条是量出来的不是设计出来的**：只抬号不够 ——
把 B 那一版抬到 rev 3 之后，`plan.rs` 的 P11 仍然每次都拦着（判据是"对面记录是删除态且本机脏"，
与编号无关），于是 Push 依旧发不出去、卡片照旧回来。也就是说"裁决"这件事在计划层根本没有输入。
因此新增 **P14**：`LocalView.decided_remote == Some(R.rev)` 时，同一件事不再重问，按编号高低走
普通路（几乎都是 Push）。编号一变就对不上 → 冲突照旧，所以这不是永久静音。
`SYNC-PROTOCOL` §7 的 P 表已加这一行，`CONFLICT-RESOLUTION` §6 那句 `rev := max(L,R)+1`
从今天起是真的（走 `Store::rebase_unpublishable_head` → `commit_edit` 那唯一出口，
旧 `payload_rev` 那条待办由 `enqueue_key` 自己标 `superseded`，没有第二套结清逻辑）。

两台真设备的实测结果（判据 P11-SR-01 已从"只打印"升到断言）：裁决后 B 的主行
`rev=3 / sync_rev=3 / 脏=false`（公告成功）、B 的收件箱 0 张卡片、同名副本 1 篇；
A 那台**仍然是已删除**（这条由既有的 `conflict_payload_e2e` 钉着，本批给它加了守卫而不是靠巧合）。
变异 **M81**（P14 短路）→ 红在三样全中；**M82**（不抬号）→ 只红在"追不平" —— 两半各自有独立证据。

**两处按实修正（都是量出来的，不是设计出来的）**：
① 落地 D2 时发现"抬号"单独不够 —— 计划层每轮按当前分叉重算，P11 的判据与编号无关，
   于是新增 P14 让"已裁决过的同一份分歧"不再重问（见 `SYNC-PROTOCOL` §7 的 P14 行）。
② 原想把"对面把我删掉的写活了"做成删除那一侧的询问卡片（临时命名 P15：把干净墓碑补进
   `local_views` + 一条新规则），**实测做不出来**：补了 8 轮之后那一侧的计划根本没有重建
   （空轮快路径 = 清单 304 且 `seq_applied` 命中就不规划），于是把那半条撤掉，不留一条
   永不命中的规则。改为在 `apply_note` 一侧先把"静默改写删除状态"这件事拒掉（`rep.skipped`，
   不报错也不覆盖）。**剩下的缺口记为 G19**（删除那一台没被问第二遍），它的解除条件要动
   §11 的 304 快路径或公告侧的可见记录，两者都属 §9 那类变更，须另批评审。

## 验证方式

* **SY-REV-01**（批二之前先写，两台真设备）：A 把一篇笔记推到 rev 5 并公告，B 追平后离线改两次 ——
  D1 生效时 B 的两次编辑必须落在 6、7 而不是 2、3，且两次都能推上去（`dirty` 归零）。
* **P11-SR-01**（已存在，判据从"只打印"升到"断言"）：裁决并追平之后两台的 `dirty_notes/outbox_pending` 必须为 0、
  收件箱里那张裁决过的卡片必须消失、`(本地副本)` 的篇数必须 ≤ 1。
* **不许回退的既有门禁**：`same_content_convergence.rs`（SY-CONV-01）、`conflict_payload_e2e.rs`
  （§6.1 副本链路）、`folder_cycle.rs`（CY-01）、崩溃注入 `crash_recovery`（抬号+入队+推出去跨崩溃点）。
* **变异自证**：把 `MAX(remote_rev, …)` 改成直接覆盖 → SY-REV-01 要红；
  把裁决里的抬号去掉 → P11-SR-01 要红回今天这个形状；
  只抬号不 `supersede_up_to` → 失败消息要红在 `outbox` 而不是 `dirty`。

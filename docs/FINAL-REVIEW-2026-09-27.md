## 一、产品视角：交付的是不是用户要的那个东西

用户要的是：**本地优先 + WebDAV 同步 + 应用级代理 + 跨平台原生感 + 自动同步 + 数据安全优先**，
"像 Apple Notes，但数据在自己服务器上"。终态是"能自测的都自测通过，交给我稍微测一下就能生产用"。

| 要的东西 | 现在到底有什么 | 用户还感觉缺什么 |
| --- | --- | --- |
| 本地优先 | 全功能离线可读写已验（纯黑盒 UAT 11 轮全绿，独立空库）；同步失败不外溢成本机 | 无 |
| WebDAV 同步 | 两台真设备 + 真 TCP 服务器收敛、冲突、删除防复活、断点续传、附件跨设备，都有门禁 | **真实服务器矩阵**（Range/MOVE/条件请求各家差异）一台都没测过 |
| 应用级代理 | 配置 → 出口客户端 → 真请求这条边今天起有差分门禁（含"撤掉代理必须失败"） | SOCKS5 与代理鉴权（407）端到端未验；填了代理口令的失败出现在**同步时**而不是**保存时**（代码里有明确理由，但体验上仍是"我存了它才告诉我") |
| 原生感 | Windows 真窗口 9/9（真 `invoke`、真 SQLite、CSP 生效），托盘 + 全局快捷键在跑着的壳里验通 | macOS / Android / iOS **零真机证据**（B1） |
| 自动同步 | 后台轮次、退避、追平进度可见（Partial 报"正在同步"而非"已同步"） | 无 |
| 数据安全优先 | 备份三道闸门、崩溃注入 9+1 点真杀进程、删除/Tombstone、附件内容寻址复验；本轮又补了"没有替代就不销毁"与 blob 回收的安全半（隔离 30 天才销毁） | 回收**只碰本机盘**：服务器上的孤儿对象没人管；且触发点在附件轮里 ⇒ **没配同步账户的设备不跑 GC**（见 G1 的边界） |

产品经理最不满的两件事，写在前面而不是藏在末尾：

1. ~~**G1 附件回收没实现**（`attachment_refs()` 无生产调用者，全仓没有回收 blob 的后台任务）。
   用户长期用下来 `attachments/` 目录只涨不删。ADR-0009 之前把删除规则当已生效的法律写，
   本轮已改成"设计，尚未实现"并补了它与新磁盘体检必须一起设计的原因。~~
   **已解除（2026-09-28，同一批决定里的第 2 条）**：回收做了"安全的那一半"—— 零引用 + 服务器已确认有副本
   的行先**挪**进 `attachments-quarantine/`（字节不销毁），宽限期 30 天过完且**仍然**零引用才删行再删字节；
   撤销期内被重新引用的那份**本地挪回、一次网络都不打**（跳过拉取有读侧的持久来源，且挪回前复算哈希）。
   判据 FT-ATT-29 / 29s / 30 / 31 / 32 / 33（六条 host 注入 + 两条存储侧，变异 M32..M40 逐条打红过）。

   的设备不跑 GC**（那条盘还是会一直涨），解除条件是把它挂到一个与同步无关的清理节律上。
2. **G2 `missing`+`absent` / `missing`+`error` 是终态，没有过期政策**。一次瞬时 404（服务器维护、
   根路径写错、恢复中途）之后，那张图在任何自动路径里都救不回来。今天的行为是**诚实报错**
   （不再是"available 的谎"），但"诚实的坏"仍然坏。要么给这两对状态一个带意图的重启路径
   （用户在界面点"重试这个附件"），要么给它们一个过期时间 —— 这是个产品决定，见 §五 D1。

## 二、架构视角：重复实现 / 跨层依赖 / 状态泄漏 / 隐性耦合 / 破坏不变量

**结构上没有新增违规**（arch-check 29/29 包含"只向下依赖""前端不许有 WebDAV 逻辑""同步协议只有一份实现"），
本轮新增/改动的东西逐个说：

* **磁盘体检 `App::sweep_lost_local_blobs(cap)`**（`crates/notera-host/src/lib.rs`；本轮审查时它叫 `demote_lost_local_blobs`，2026-09-28 因为 G4 改成收候选上界，见 4.1）
  * 它把 `local_state` 变成一个**由后台推导**的值 —— 这一点是本轮最大的架构性变化，之前
    `local_state` 只由传输代码写。任何将来读它做决策的地方（尤其 GC）都必须接受"它会自己变"。
    已写进 DATA-MODEL §8 与 ADR-0009 的更正里。
  * 判据没有第二份：`sha256 是身份` 这条规则在下载侧、上传复验、读侧 `attachment_data`
    三处都成立，且读侧那次是本轮回审补上的 —— **补之前界面能把错字节画出来**（缓存按 sha 存整个会话）。
  * 降级用的是既有的 `Store::set_attachment_states`，没有第二条状态机；补齐走既有下载队列（含 Range
    续传），没有新增传输路径。
  * 泄漏点：**没有**。坏文件挪成 `<sha>.corrupt` 不在正式位置，导出/备份/读路径都取不到它
    （导出以库为准，见 store.rs 那段"本地附件 sha 清单"的注释）。
  * 成本上的隐性耦合（G3，**2026-09-28 已解除**）：账上 `size` 记错而内容其实好的那一行，原本会
    **每轮整份读 + 重哈希**，因为复算通过后没把 size 写回去。上界是每条 32 MiB / 20 s。现在那条分支
    把哈希相符算出来的真值回填成登记尺寸（`Store::set_attachment_size`，只改那一列、字节不碰），
    于是这一行下一轮回到只 `stat` 的快路；这一步必须有，因为登记那条路的规则是 `MAX(旧, 新)` —— 只许涨
    不许落，偏大的声明值它自己永远纠不掉。门禁 FT-ATT-20 + 变异自证 M19。
  * 每行一个写事务 + 候选集不分页（G4，**2026-09-28 已解除**）：原本误删整个 `attachments/` 目录时
    一轮里会有 N 次 rename + N 次提交。现在候选按 `cap` 分页（常驻循环传 200），降级是**一次**批量写事务。
    降下来的行当轮就进下载队列，这条不变。
* **`put_attachment` 的 405/412 分支**：三种结局（成功 / 被拒 / 其他错）现在**共用同一次复读**，
  没有第二套校验逻辑。SYNC-PROTOCOL §13 那句话也按事实收窄了 —— 承认"HEAD 判存跳过上传"
  记下的 present 是**借来的**，代价写在文档里（消费侧靠下载复验兜住；第二次上传撞同一坏对象未覆盖，G5）。
* **内容不符 → `remote_state='error'`**：这是本仓**第一次**写这个状态值（此前只有 present/absent 被写，
  schema 里的四个值之一一直空着）。选它的理由写在代码注释里：它同时把这一行从两个队列里摘出去，
  而"服务器给的东西与 sha 不符"本来就是一句关于**远端**的结论。
* **注入器的 `hang_for`**：与 `status_for` 共用同一个 `rule_hit` 解析器，语法只有一份实现；
  `post:` 前缀在 hang 这条路里被剥掉且不参与判定 —— 这个事实现在被一条单测钉住（G6 记录了它为什么值得钉）。

驳回的审查意见：**"磁盘体检会把独家字节降级、被 404 吸干"**。机制不成立 ——
`attach_blob`（`store.rs:568`）与 `restore_blob`（`:666`）写的是 `remote_state='unknown'`，
而体检只扫 `available ∧ remote_state='present'`；审查引作证据的那处测试在两行之前刚把远端显式设成 `present`。
**但它顺带指到的"哈希不符就直接删"是真的**，已经按"没有替代就不销毁"改掉（FT-ATT-12c 钉住）。

## 三、测试视角：机器还没证明什么

### 3.1 本轮新抓出来的假门禁（比缺测试更糟）

`ui_read` 的断言原来写成

```rust
assert!(got.get("code").is_some() || got.get("data").and_then(|v| v.as_str()).is_none(), …)
```

而 `commands::dispatch` **没有** `{ok, data}` 那层包（`j()` 就是 `serde_json::to_value`）：
左半对任何错误恒真、右半对任何成功恒真 —— 这条断言数学上不可能失败，却被算进了"§27 有 9 条实证"。
按 §45"不会红的测试比没有测试更糟"，它现在改成打**精确错误码 + 精确状态对**
（`attachment_for_state` 对不存在的行也返回值，只判 `≠ available` 会放过"整行没了"这种回归），
断言消息只打键名和长度。四处同修，并用变异自证 M13（缺文件也回字节）证明它有牙齿。

同类被一起修掉的：FT-ATT-17 里"附件轮在 per_request 内放手""两轮并发"当时只是文档声称 ——
现在两轮耗时从同一起点量，断言附件轮落在 `[budget/2, budget×2]` 且文本轮结束时附件轮还没返回。

### 3.2 §27 / §28 的实证账（原指令两张清单）

* **§27 附件故障注入十条：9 行有实证**（TEST-PLAN「§27 十条 —— 实证账」逐行标了证据与变异次数，
  M1..M16 共 16 次变异）。其中四行只覆盖了一半，写在同一张表里不当已收口：
  上传中断只有半上传形态、404 只有下载侧、412 只有第二次上传之外的部分、"文件不存在"的删除侧语义未测。
* **§28 代理故障注入十二条 + 那句保证：9 行有门禁、2 行部分、3 行未覆盖**
  （SOCKS5 端到端、407 错误密码、真 TLS 握手失败）。根因是同一个：**工装的"代理"是源站自己扮的**，
  且没有 TLS。解掉它需要一个新的转发代理 harness 组件（客户端 → HTTP/SOCKS5 代理，可选 407 → 独立源站，可 TLS）。
* **一条更大的账**：TEST-PLAN 记法表里写的 `times`（命中次数，防粘连）**工装里没有这个字段**，
  所以 SY-FAULT-02/03/04/09/10 那些按 `times=` 写的行**都不能按字面跑**。之前没人对过这张表，
  本轮对完并写在「这张记法表自己的账」里。

* **补证据补出来的一条真缺陷（0.0.27，判据 FT-ATT-39）**：任务 #54 那一格的尾巴写着"真起两个 OS 进程跑同一轮 GC 仍未验"。
  为了把那句话拿掉，写了两个真进程在同一数据目录上抢同一批 sha 的门禁 —— **它第一次跑就红了，而红的不是认领次数，是字节不见了**：
  `quarantine_move` 在 `rename` 之前有一句"目标已存在就先删掉"（本意是同 sha 覆盖旧副本，内容寻址下覆盖不亏），可那两个位置是**共用一个落点**，
  于是当 A 已经把字节 rename 进隔离区、而 B 早一步过了"正式位置还在吗"那道检查时，B 删掉的正是 A 刚落地的**唯一一份**，
  紧接着 B 自己的 rename 因为源不存在而失败 —— 正式位置空、隔离区也空，而这一行随即被写成"已隔离"。
  用户侧的形状是"图片块还在、字节永久没了"，落在优先级第一格。修法只有一句：**去掉预删，让 `rename` 自己去替换目标**
  （Unix 与 Windows 的 `std::fs::rename` 都是原子替换），于是"挪不动就本轮不收这一条"这条顺序不再有例外。
  判据四条（认领总数 == 候选份数 / 没有哪一份还压在正式位置 / 每一份的字节都在隔离区且一字不差 / 销毁只数到一次且两边事后各读各的账都是
  `absent|absent`）；变异自证 **M54**（把那句 `remove_file` 加回去）红在第三条，**M53**（把"账上真认领了几条"换成"我搬了几条"）红在第一条，
  实测父 24 / 子 22 / 候选 25 —— **而同一条 M53 打在 FT-ATT-37（同进程两 store）上是绿的**，所以这一格不是重复劳动，
  它看着见的那条边同进程那条看不见。复现率按实记：修前 1 份字节 **2/8**、25 份 **4/5**（单轮最多 14 份消失），修后 **24/24 绿**。中间还有一次是**夹具自己欠的账**：修后仍有 3/33 轮红在"子进程没拿到销毁清单"，插桩说 `账上可准入/服务器确认在 = 1/0` 而同一瞬直接再问服务器 `Ok(true)` —— 那一行由赢的一家写账，输的一家抢在它提交前读到期清单就读到空；于是认领与销毁之间补了 `both1` 这道栅栏。
  工装两条也记着：① 父进程 panic 之后子进程会一直堵在栅栏上，同时**占住测试二进制**，下一次构建报 `Permission denied`，
  看着像门禁红了 —— 栅栏因此加 `stop` 文件与 8 s 上限；② 我第一版插桩写成 `format!("{ready}/{verified.len()}")`，
  格式串非法**根本没编译成功**，连着 6 次"红"全是构建失败 —— 探针要先验自己。

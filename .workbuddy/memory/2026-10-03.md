### E2EE：先摸清现状再动手（用户拍板：恢复码+口令双轨、全量迁移历史）

**ADR-0002 早就把话说尽了**：「v1 固定 alg=none，结构预留功能默认关闭」，理由是

**实测摸底（四条，缺一不可）**：
| 项 | 状态 |

**已交付：任务 1 密钥托管层**（`crates/notera-crypto/src/vault.rs` + `recovery_wordlist.rs` + `tests/key_vault.rs`）

## 第四轮：E2EE 接进同步引擎（任务 2/3 完成）

### 上行/下行的真正接插点（摸出来的，别再猜）

链路：`notera-sync/lib.rs` run_round →③ push 段（第 711 行起）
`local.envelope_wire()` 拿明文信封字节 → `remote.probe_record_etag()` → `remote.put_record()`
→ （webdav 层 `atomic_write` / `put_cond` 发 PUT）。

**接插点选在 `envelope_wire()` 与 `probe_record_etag()` 之间**，理由是硬的：
条件写用的 ETag 属于服务器上**当前**那份。若先探 ETag 再密封，两次看的不是同一个对象
⇒ CAS 拿着明文版 ETag 去改密文版那行 =假 412 或覆盖掉别人的并发写。

**为什么不改 `notera-store` 的 `envelope_wire`**：`envelope_wire` 同时被"写后复验"和"上行"复用，
在那里密封会让**落库读回**也变密文 —— 那是 ADR-0016 本地静态加密（独立议题），两件事混一起就分不清哪条链在起作用。
⇒ 新模块 `crates/notera-sync/src/sealed.rs`。

### sync 的依赖隔离没被破坏

`notera-sync/Cargo.toml` 原本刻意只依赖 `notera-core`（注释：不依赖 store/webdav/config）。
加 `notera-crypto` **不违反**这条 —— crypto 自己的 crate 文档写着"不得依赖 store / webdav / sync"，
它是纯密码学原语 + 记录信封，不知道远端存在。另加 `tracing`（密封失败要留痕）。

### 引擎挂载方式：Arc<RwLock<Option<Arc<KeyVault>>>>

**不塞进 `EngineConfig`**：Config 是"构造时定好、不中途变"的，而解锁/锁定是运行中反复发生的
（解锁一次、锁屏自动上锁），放 config 就得为此重建整个引擎。
`set_vault(None)` = 关闭加密 ⇒ **存量调用方零改动**。

### 踩到的真回归（这次最有价值的一条）

接完密封后 `cargo test -p notera-sync` **4 条既有单测红了**（remote_new_note_is_pulled_and_applied 等），
读数是 `信封结构不合法: 信封缺少 kind`。

根因：引擎那批毫秒级单测的 wire 夹具是 `{"rev":3}` / `{"i":"s1"}` 这种**极简形状，不是合法信封**。
我第一版在 `open_incoming` 里先跑 `Envelope::from_wire`，于是**"没启用加密"也换了行为** —— 那是回归不是收紧。

修法：拆出 `looks_encrypted(wire)`，**只读 `enc.alg` 一格，不做全信封校验**；
`open_incoming` 在 `looks_encrypted == false` 时**完全透明旁路**。
⇒ 已加门禁 `未启用加密时对任意形状都是旁路`（喂 5 种形状含空串/非 JSON，逐字节断言原样返回）。

**教训**：给既有数据通路加校验时，"未启用新功能的那条路必须字节级不变"本身就是一条要钉的判据。

## 第八轮：装包实测的三个反馈（16:40~17:30）

用户装完 0.0.58 后给了三条：① 打开程序挂着一个终端窗口；② 清除数据后列表仍是

保存反馈、编辑器操作、退出与数据安全；并说"说不上来具体路径"）。

### ① 终端窗口：`windows_subsystem` 写错了地方（两版都错）

**我第一版写成了 Cargo.toml 的 `[[bin]] windows_subsystem`** —— 那是**错的**：
`windows_subsystem` 是 **rustc 的 crate 属性**，不是 cargo 的 manifest key。
cargo 只给一条 `unused manifest key: bin.0.windows_subsystem` 警告，
而**exe 仍然是 console 子系统，照样弹窗口**。那条警告淹在编译日志里，
极易误判成"已生效"（我差点就这么交付了）。

正确写法在 `src/main.rs`：

```rust
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]
```

`not(debug_assertions)` 是有意的：`cargo run` 调试时保留控制台，panic 第一现场才有地方看。

**验证方式（比"改了没"可靠）**：读 PE 头的 Subsystem 字段 ——
`pe = buf.readUInt32LE(0x3c)`，`sub = buf.readUInt16LE(pe + 24 + 68)`，
2 = console（会弹窗）、3 = GUI（不会）。本轮读数：3 ✓。

### ② 清除数据不生效：三处界面状态各说各话（真 bug，我上一轮的实现漏了）

清库只动了**库**，三个界面状态**一个都没被告知**：

- 侧栏 `allCount` / `trashCount` 读 `settings.stats`（只在 `App.vue:221` 启动时取一次）
- 列表读 `notes.rows`
- 编辑器握着 `editor.blocks`（还挂着"这条在最近删除里"的**假提示**，而它已被永久删除）

**另有一处隐藏分支漏改**：`notes.load()` 只在"列表非空且选中项不在列表里"时迁移 `selectedId`，
**列表为空的那一支没有** ⇒ 清库后 `selectedId` 仍指向已删的 id，编辑器照旧渲染它。

修法（`SettingsView.doErase`）：`editor.open(null)` → 并发 `loadStats / notes.load / conflicts.load`。
顺序不能反：先关编辑器，否则 `load` 会把 `selectedId` 迁到新列表第一行、编辑器还开着上一篇。

门禁 `src/stores/eraseAllData.spec.ts`（6 条）。变异：撤掉那个空列表分支 ⇒ 精确 2 条红。

### ① 同步一直转：启动路径上有一句无条件 `syncNow()`

`App.vue` 的启动块里是 `void sync.syncNow();`，**完全没看有没有配账户**。
没配时核心回 `no_account`，而那条错误**不会把徽标从"正在同步"带走** ⇒
装完第一次打开，侧栏那颗徽标就在转，而且用户没配同步、那颗圈在暗示"有东西在上传"。

改成：
```ts
void settings.loadAccount().then(() => {
  if (settings.hasAccount) void sync.syncNow();
  else sync.markNoAccount();
});
```
**顺序有讲究**：`loadAccount()` 是异步的，必须等它落地再判 `hasAccount`；
不 await 就读的话它还是 false ⇒ 用户配好了却不同步。

核心侧本来就对（`src-tauri/src/lib.rs` 的 `Ok(None) => {}` 守卫：无账户就不启动引擎），
问题**只在前端**。那两个 20/25 秒的 `tokio::interval` 轮次也只在有 remote 时才起。

真机读数：徽标 6 秒稳定 `idle,idle,idle,idle,idle,idle`，`aria-busy=false`。

### 一处旧测试逼出来的设计决定

改完 `275` 条里红了 1 条：`app.spec` 要求"本地服务没起"时徽标显示**离线**。
⇒ 于是定了一条优先级：**链接不可达 > 未配置同步**。
"本地服务都连不上"是更前置的条件（能不能读到笔记还没保证），
此时报"未配置同步"是**转移焦点**—— 用户会去设置里翻同步，而真正的问题是服务没起。
而 `unreachable` 的字形 `○` 同样是静止的，不违反"没配就静止"这条要求。
实现在 `markNoAccount()` 里加一个 `link === 'unreachable'` 的前置判断。

### 补记：`windows_subsystem` 那个"没生效"是我**验证方法错了**（10-04 中午）

起因：本轮出包后我又去读 PE 的 Subsystem，读到 2，于是以为上轮的修复失效了，
于是又改了一遍 `main.rs`（去掉 `cfg_attr`）。**改完还是 2。**

于是做了个最小探针 crate（`.logs/subsys-probe`，`#![windows_subsystem = "windows"]` + `strip = true`
+ GNU 工具链），**它也读到 2** ⇒ 两种写法都被我判成"无效"。

**真相**：`objdump -p` 明确写着 `Subsystem  00000002  (Windows GUI)` ——
**2 就是 GUI**，而我一直以为 3 才是 GUI。

- Windows 的枚举：`1 = native`、`2 = **Windows GUI**`、`3 = Windows CUI(console)`。
- **PE32+（64 位）的 Optional Header 里 Subsystem 在偏移 68**（`pe + 24 + 68`）——
  这一点我记对了，**读出来的值我也读对了，是我对"2 是什么"的解读反了**。

所以：**上轮那个终端窗口修复一直是有效的**，是验证代码把 GUI 误判成 console，
害我又白改了一遍。两处修正都留在仓库里了（`#![windows_subsystem = "windows"]` 无条件版是对的）。

⇒ **教训：验证 PE 字段不要手写偏移去猜语义，用 `objdump -p` 读，它会直接标出名字**
（`(Windows GUI)` / `(Windows CUI)`）。本机的 objdump 在 WinLibs 里：
`%LOCALAPPDATA%\Microsoft\WinGet\Packages\BrechtSanders.WinLibs.POSIX.UCRT_*/mingw64/bin/objdump.exe`。

⇒ **第二个教训（更值钱）**：我因为"验证读数不对"就去质疑已经交付的修复 ——
**先怀疑验证本身**。正确顺序是「换一个独立来源复核（objdump / 直接运行 / 问用户」），
而不是「再改一遍生产代码」。这次多花了一轮编译，
而且如果 objdump 也不在手边，很可能就一路改下去、把一个本来正确的东西改坏。

### 第九轮补记：门禁写法的三次翻车（同一类根因）

写 `syncIdleAndSidebar.spec.ts` 时，三条判据连续假红，**根因都是"用文本形状推断语义"**：

1. `settings\s*\.\s*loadAccount\(\)[\s\S]{0,320}?\)\s*;` 窗口被中间那段注释撑爆，截不到 else ⇒
   改锚在 `settings\n.loadAccount()` 的链式形态。
2. 裸搜 `loadAccount()` 会撞上**另一处**独立的 `void settings.loadAccount();`（只读账户、不触发同步）⇒
   改用**行序**判（`.loadAccount()` 行号 < `.then(` 行号 < `if (settings.hasAccount)` 行号），最稳。
3. "那三处 syncNow 是不是顶层语句"靠"上一行是不是 if/=>/{"推断，而 F5 那处上一行是
   `event.preventDefault();` ⇒ 假红。**改成钉"三处入口都还在"** ——
   那才是这条判据真正想守的东西（自动同步被门控 ≠ 手动同步被删掉）。

⇒ 结论：**判源码结构优先用「行序/精确锚点」或「钉住要守的性质」，别用大窗口正则或上下文形状推断**。
大窗口与形状推断只是"看起来更宽容"，实际会转移到别的行/别的语句上。

### 第九轮补记二：出包脚本又缺一颗 shim（cargo）

第一次跑 `build-dist.mjs` 直接失败：
`failed to run 'cargo metadata' command to get workspace directory: ... program not found`

`tauri` 是 **node 写的**，它起`cargo metadata --no-deps` 定位 workspace ——
那是**不带 shell** 的 `Command::spawn`，继承本脚本 env，而 cargo 在 `~/.cargo/bin`
（不在 Git Bash 默认 PATH）。

**两次都错在同一个点上：**
1. 第一版只加 node/pnpm/windres，**漏了 cargo**。
2. 补了之后写的是 `cargo.cmd` —— **仍然失败**。因为
   `Command::new("cargo")` 不带 shell 时，Windows 的 `CreateProcess`
   **不会把 `foo.cmd` 当可执行文件解析**（PATHEXT 只对 cmd 内部/交互式查找生效）。
   ⇒ shim 目录里必须放**真的 `cargo.exe`**（用 `copyFileSync` 复制过去）。

⇒ 归纳成一句：**给"不带 shell 的 spawn"准备的 shim 必须是 `.exe`；给 cmd 的才可以是 `.cmd`。**
node/pnpm/windres 那几颗是走 cmd 的（`shell: true`），所以 `.cmd` 没问题。

⚠ 本轮还撞到**shell 快照文件持续报 `fnm: command not found`**
（`~/.workbuddy/shell-snapshots/snapshot-bash-*.sh` 里的 fnm hook 挂了），
导致一批Bash 命令 exit 127。绕法：改用 **PowerShell 工具**跑（`Set-Location` + `$env:PATH=...`），
出包 5 分钟一次跑通。以后遇到这个快照报错，直接换 PowerShell，不要在 Bash 里反复重试。

⚠ 但**不要用 PowerShell 写记忆文件**（见下条）。

### 记忆文件被 PowerShell 截断过一次（已修复）

用 `Add-Content -NoNewline` 往记忆文件追加，**把整个文件截断了**
（382 行← 原本 661 行，第八轮整段丢失，尾部还进了 GBK 乱码）。
原因：那个环境里的 `Add-Content -NoNewline` 不是"追加"而是"重写"。

修复办法：找首个 U+FFFD 替换字符（编码坏掉的标志），回退到它之前的换行再截断。
⚠ 注意：**别在正文里直接写那个替换字符**（我第一次写教训时顺手把 `U+FFFD` 打了进去，
于是文件里长期带着一个"坏字符"，下次真出现编码损坏时反而定位不到真正的坏点）。
好在内容本身没丢。
好在那些内容**在会话上下文里还在**，手写回去即可。

⇒ 两条纪律：
1. **写记忆文件一律用 node 的 `fs.appendFileSync`**，不要用 PowerShell 的 `Add-Content`。
2. 这类文件**不在 git 里**（`git status` 查不到），所以截断了没法 `git checkout` 回来。
